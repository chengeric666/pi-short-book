Preface

怎么读这本书

每一章先给你看一个现象，再告诉你这一步之后系统里多了什么状态。中间会插入对照实验：失败样本、加约束、再变像样。公司决策章故意放在机制之后——若你还没看清「提交」与「副作用」的边界，任何采纳清单都只是安慰。

「Pi」不是单一产品。它是一个 MIT 许可的 TypeScript 单体仓库：编码智能体 CLI、统一模型 API、以及实验性的持久化运行库 @earendil-works/pi-durable。把它们当成一个 SaaS 黑盒，就会误判你要自己补齐的治理面。

正文用完整叙述句。图注、清单与警告框用短句（ASD-STE100 风格）。代码、路径、包名、URL 保持英文。版本锚定编码智能体与 Durable 包线 1.0.4（2026-10-05）；Durable 技术手册覆盖 1.0.3，冲突处标 [manual vs code]。互动控件（步进器、对照切换、决策树、清单计分等）用来复现「失败→加约束→变像样」的阅读节奏；它们不是装饰，而是实验装置。

Chapter 1

它只是在跑一个循环

剥掉产品外壳之后，编码智能体几乎总在做同一件事：把用户的话交给模型；若模型要工具，就执行并把结果贴回对话；再问模型下一步——直到它不再要工具。Pi 把这件事做成可替换边界的小循环，而不是一个塞满计划面板与权限弹窗的产品内核。

可观察现象：你说「读 README 第一行」

先别急着谈架构标签。你在屏幕上能直接看见的，只有几类东西：你的输入、模型吐出的字、偶尔出现的工具调用卡片、以及最终一段像人话的总结。公司评审若从「多智能体编排」之类大词开始，很容易跳过这些可观察对象，也就跳过了真正决定可靠性的状态边界。

在终端里输入这句话时，你看见的是流式文字与偶尔闪过的工具调用。系统内部并没有「理解任务」的独立模块。它做的是：把你的输入写成一条用户消息；组装一段上下文（系统提示、项目说明文件、工具描述、近期对话）；调用模型 API；解析返回里的工具调用；执行；再拼回上下文。若模型给出最终自然语言且不再请求工具，外层回合结束。

Pi 把「外层回合真正空闲」标成 agent_settled。这与某次内部模型尝试结束的事件不是同一件事。若你的宿主程序要等「没有排队工作、可以接受下一条用户输入」，应等待 agent_settled，而不是某个更早的结束信号。

为什么这样管用。 现代编码模型已经在大量「工具调用格式」上训练过。你不必先造一个巨大的产品内核，也能让模型读改文件、跑命令。真正难的是脚手架：会话怎么存、上下文怎么裁、扩展怎么接、进程挂了进行中的工作怎么办。后面各章就是在剥这些层。

把循环想小，还有一层产品含义：功能膨胀会把「默认行为」变成隐形合同。计划模式、子智能体面板、权限弹窗一旦进入内核，公司就得跟着厂商的政策模型走。Pi 选择把这些留在扩展与例子里，等于把合同表面推到你的仓库。好处是可审计、可替换；坏处是没有「开箱合规」。若你的组织习惯购买一体化代理产品，这种极简会显得「缺功能」——其实是缺默认治理，而不是缺循环本身。

1.0 发布把编码智能体描述为「硬化、最小、可扩展、人与企业可以依赖」的运行框架，同时把 Durable 标成实验性。同一周内 Cloudflare 又发布了 PiHarness beta。对公司读者，时间线很重要：你不是在评估一个静止了三年的框架，而是在评估一条高节奏发布线。五天内从 1.0.0 到 1.0.4，意味着修复快，也意味着升级成本真实存在。后文成熟度章会把「patch 里出现 Breaking Changes」写成风险项，而不是脚注。

「Pi」拆成包之后

在仓库里，名字指向一组包：pi-ai（多提供方模型与流式协议）、pi-agent-core（几乎无状态的循环）、pi-coding-agent（你安装的 pi CLI：会话、扩展、TUI、RPC、SDK）、pi-durable（实验性持久化运行库）、chord（应用组合与文档跟踪）。1.0 是对编码智能体及兄弟包的稳定性声明；同一发布把 Durable 标为 experimental——二者不要混为一谈。

Chapter 2

一次轮回里到底发生了什么

现象层看完，下一层问：一次用户输入之后，系统里按时间顺序多了哪些可观察对象？下面用步进器把「读 README」拆开。每一步结束时，会话文件、内存队列或 UI 上会出现新的东西——这正是后续「崩溃丢什么」实验的对照基线。

逐步展开：用户消息落盘 → 上下文组装 → 模型流 → 工具调用 → 结果写回 → 最终答复 → agent_settled。 资料：how-pi-works、sessions、sdk；手册一次捕获：两轮约 29 事件、四次落盘（定性形状）。

这一步之后系统里多了什么

步进器每前进一步，请强迫自己说一句完整的话：「这一步之后，多了什么、仍停留在内存里的是什么、外部世界变了没有。」说不出来，就说明你还在看界面动画，而不是看状态。

用户消息写入会话后，磁盘上多了一条带父指针的 JSONL 条目——分支导航依赖的就是这些父指针。上下文组装本身通常不单独落成「一条用户可见消息」，但它决定了模型「看见」的窗口：系统提示、AGENTS.md / CLAUDE.md、SYSTEM.md、技能描述（渐进披露）、工具表、近期对话。压缩触发条件是 contextTokens > contextWindow − reserveTokens（默认 reserve 16,384）；压缩会总结旧消息并保留近端，原始条目默认不删除。

模型流式返回时，UI 上先出现局部文本；若出现工具调用，运行时执行默认工具（read / write / edit / bash）或扩展注册的工具。工具结果写回后，内层时钟可能再转一圈。整轮结束的信号是 agent_settled。手册记录的一次假模型捕获说明：流式更新远多于「最终答案」事件——宿主若只订阅稀疏事件，会误判空闲。

Chapter 3

会话为什么是树

线性聊天日志足够「回看」，但不够「试另一条路」。Pi 编码智能体把会话存成树：每条条目有父节点。于是 /tree 能导航替代分支，/fork 能开新会话文件，离开分支时可总结。树不是装饰——它是「可后悔的探索」的数据结构。

会话文件落在 ~/.pi/agent/sessions/<cwd>/ 一类路径下，格式为 JSONL。你改提示、重跑工具、从某条助手消息分叉，本质上是在树上长出新枝。压缩不砍掉旧条目，所以「看起来变短的上下文」与「磁盘上仍在的历史」可以并存——这既利于审计，也意味着会话文件可能含密钥，分享前要当心。

再看一次「父指针」带来的操作后果。当你在某条助手消息上后悔，你不是在改历史，而是在旁枝上重写未来。主链仍可导航回来；总结离开的分支时，你可能把一条旁枝压成较短的叙述，但原始条目仍在。这种「不删除的后悔」与 Git 的可达对象很像：用户界面可以显得干净，存储层仍记得你试过什么。对研究与排错极好；对「被遗忘权」类合规则需要额外策略。

主链与分叉枝共享祖先；分叉不复制整棵历史的语义在 Durable 里更极端（见第 10 章）。 资料：docs/sessions.md。

四种入口共享同一套会话与循环语义，只是把循环暴露给不同宿主：交互式 TUI；print/JSON；RPC（JSONL over stdio，严格 LF 与 id 关联）；SDK（createAgentSession()）。RPC 换进程隔离；SDK 换进程内控制。SDK 里 Codemode、tool_search、MCP 默认不开启——这是刻意的最小默认，不是疏漏。

树结构还改变了「分享」与「导出」的含义。/export 可以写出 HTML 或 JSONL；/share 可上传到私有 gist，或在登录 Radius 后作为 Radius artifact。会话文件里可能含有密钥、令牌碎片与内部路径。树让你容易分叉探索，也让你容易在不知情时把整枝历史交出去。公司若把 Pi 当日常驱动，应把会话目录纳入数据分级：哪些可进工单附件，哪些必须留在本机或受控卷。

压缩与树交织时，会出现一种直觉错位：屏幕上的上下文变短了，磁盘上的条目却还在。这对审计友好，对「删掉敏感回合」不友好。Durable 一侧更加极端：公开材料写明尚不能删除对话，重置只移动 head。若你的合规要求是「可擦除」，两条产品线都需要你在宿主层另建封存与脱敏策略，而不是假设框架已提供。

Chapter 4

工具：意图先于执行

在编码智能体里，工具调用看起来像「模型说了就算」。在 Durable 里，设计被推进一步：先把意图提交进可恢复状态，再执行副作用。即便你暂时只用 CLI，理解「意图与结局分离」也很重要——因为崩溃对照实验的关键就在这里。

默认四工具与暴露模式

默认工具是 read、write、edit、bash。扩展可以 registerTool，并选择暴露方式：直接、仅模型、codemode、延迟加载或隐藏。若 tool_call 处理器抛错，调用被阻断（fail-closed）。没有内置的「每次工具弹权限」——官方安全文档写明：Pi 不按工具调用征求批准；你应容器化，或用扩展例子（permission-gate、protected-paths、confirm-destructive）自己做门闩。

图 6

工具调用：从模型文本到副作用

CLI 路径上执行前可有扩展钩子；Durable 另有「意图先提交」的硬规则。 资料：extensions.md、security.md；Durable manual §5–6。

Codemode：沙箱里的 JavaScript

Codemode 让模型写一段作为 async 函数体的 JavaScript，在 QuickJS 中运行：无 Node API、无文件系统、无网络、无定时器；对外只能通过 tools.* 与 models.*。文档强调：工具调用是真实发生的——失败前已做的调用不会自动撤销。store() / load() 把小状态存成跟随分支的会话条目。

把 Codemode 当成「更安全的 bash」会误判。沙箱挡住的是 Node 能力，不是通过 tools 触达的真实世界。一次失败的脚本仍可能已经调用了会写文件或打 API 的工具。公司政策应把 Codemode 与普通工具调用放在同一审批与审计面上，而不是因为「QuickJS」三个字就降级管控。

MCP：配置在信任之后

1.0 起原生 MCP（stdio 与 streamable HTTP，含 OAuth 检查）以 builtin:mcp 形式进入 CLI，默认开启，可用 -builtin:mcp 去掉。用户配置在 ~/.pi/agent/mcp.json；项目配置 .pi/mcp.json 仅在项目信任之后读取。这与「最小主义」叙事有张力：播客旧说法「No MCP」已过时——核心在长大，公司策略要跟着变。

最小主义漂移本身是治理信号。当内置能力变多，默认攻击面也变多。车队镜像应显式声明启用了哪些 builtin，并在变更窗口评审新增项。SDK 嵌入路径继续保持「默认关闭」更安全；CLI 日常驱动路径则要假定 MCP 已在，除非你关掉它。

Warning

项目信任不是沙箱。AGENTS.md / CLAUDE.md 无论信任与否都会加载。把模型生成的命令与代码当不信任输入；用容器或微虚拟机隔离。

Chapter 5

扩展为什么是进程内代码

Pi 的定制面是 TypeScript 扩展、skills、packages、提示模板与主题。扩展经 jiti 加载，与智能体同进程、全权限。这不是偶然实现细节，而是「primitives, not features」的代价：你得到可编程的内核钩子；你失去「默认安全边界」。

扩展 API 包括 pi.on(event)、registerTool、registerCommand、registerProvider、registerMcpServer、registerVirtualModel、registerToolRenderer 等。仓库里有大量扩展例子（含 permission-gate、sandbox、plan-mode、subagent、git-checkpoint）。子智能体与计划模式是例子，不是内置产品功能——站点明确说跳过这类功能，让你自己建。

Durable 侧：注册表是进程内的、不持久化；对话只存扩展名；未安装则静默跳过。「没有全局钩子」。 资料：extensions.md；Durable manual §7；CF：「尚无内置审批步骤」。

对公司而言，这意味着：安全策略必须变成你发布的包与强制配置，而不是「开箱弹窗」。托管安装会钉住传递依赖；自 1.0.1 起 npm 全局安装因去掉 shrinkwrap 而不再钉传递依赖——车队部署更宜托管安装或 Nix。安装遥测 enableInstallTelemetry 默认 true；可用 PI_TELEMETRY=0 关闭。具体载荷内容据公开资料未完全证实，上线前需自行核实。

威胁模型可以写成三句，供安全评审直接引用。第一，模型输出不可信：命令、补丁与 Codemode 脚本都按不可信代码处理。第二，提示注入在安全边界之外——框架不声称挡住「网页里藏指令」这类攻击。第三，项目信任只控制部分资源加载（例如项目级 MCP 与部分 packages），不是沙箱；AGENTS.md 与 CLAUDE.md 无论信任与否都会进入上下文。于是「打开一个别人的仓库并运行 pi」本身就是高风险操作，应在容器或微虚拟机里做。

扩展例子里的 permission-gate、protected-paths、confirm-destructive、sandbox/、gondolin/ 不是装饰目录，而是官方在告诉你：治理要自己装。Durable 走得更远：注册表永不持久化，对话只记住扩展名；名字对不上就静默跳过。宿主编排若允许「可选扩展」，等于允许「可选安全」。正确的公司默认是：强制 install 一组扩展，并在 configure() 里写死，使对话无法取消门闩。

Chapter 6

实验：进程死在工具中途时，你还剩什么

现在做一次对照实验。假设模型已经决定调用 bash 去跑一条会改外部世界的命令（部署、发消息、写工单）。进程在「命令可能已经开始、结果还没写回会话」时被杀掉。问：磁盘上的会话、内存里的队列、外部系统，各自还剩什么？编码智能体与 Durable 的答案不同——这正是 Durable 存在的理由。

失败样本：编码智能体（会话文件在，进行中工作不在）

实验设定要故意残酷一点：不要选只读工具当唯一样本。只读失败时，外部世界没变，损失主要是时间；一写、一部署、一发通知，外部世界就有了「可能已发生」的分叉。框架若不能谈论这个分叉，运维就只能靠猜。

博客与手册用几乎同一句话概括缺口：编码智能体为「在你的（远程）机器上、终端里、一人驱动」而建；进程死了，你看对话记录，再告诉它继续。会话 JSONL 保住了已落盘的消息与已完成的工具结果，但不保证：内存里排队的 steer / follow-up、尚未写回的流式半截、以及「工具已经启动」这一事实。于是恢复路径是人类操作，不是调度器自动续跑检查点。

加约束之后：什么必须先变成提交

Durable 的回应不是「把整个 Node 堆快照下来」，而是收窄可观察面：凡是 UI 或其它客户端能看见的，必须先进入原子提交。流式局部结果按节流写入（默认约每 100 ms；[manual vs code] 自 1.0.3 起可通过 partialIntervalMs / outputIntervalMs 配置，默认仍为 100 ms）。工具意图在执行前提交。应用状态与条目、任务记录同一提交。于是「死在工具中途」时，你至少还剩一张诚实的支票：系统记得自己打算做什么；至于做了没有，要靠重放策略与你的幂等设计回答。

对照实验要读出三层结论，而不是停留在「Durable 更好」。第一层：编码智能体优化的是人类在场的终端劳动；崩溃后的续跑是对话行为，不是调度行为。第二层：Durable 优化的是应用在场——Slack、值班、长调查——崩溃后的续跑必须机器可做。第三层：两边都不替你解决外部世界的 exactly-once。谁先扣款、谁先建单、谁先发消息，仍然要靠幂等键与补偿。若有人把「Durable」听成「自动恰好一次」，那是营销听力，不是规格听力。

Kubernetes 上的轶事有助于建立场景感：有人曾用 DBOS 一类方案做会话存活，再换成 Pi Durable。这不是基准测试，只说明需求真实：Pod 被驱逐时，智能体若只能「留下聊天记录」，值班机器人就会停在半句话。换成提交化任务后，唤醒路径变成 reopen 与调度，而不是等人上班点继续。你的公司若没有这类场景，路径 1/2 可能已经足够，不必为了「新词」上实验库。

Chapter 7

Durable 的一条规则：只有提交后的状态可观察

规格里有一句被手册反复引用的核心规则：Session 原子地提交不可变条目、完整任务记录、以及 Chord 跟踪的文档；只有已提交状态可观察。八条不变量围着它，其中包括：先存后发、禁止易失发布、效果留在事务外、ID 不可变、不确定的存储失败会毒化 Session（必须关闭再开）。

把这句话翻译成工程直觉：客户端看到的每一个像素级事实，都应该能指出一次提交作为原因。你不能先把「正在打字」的半截真相广播出去再希望磁盘跟上——那会在崩溃后留下幽灵 UI。相反，先写入存储，再发布。效果（HTTP、bash、发邮件）不在事务里跑，否则你无法定义回滚；但意图与结局必须在事务里各留痕迹。

不确定的存储失败会毒化 Session：必须关闭再打开。这听起来粗暴，却避免了「半提交真相」继续向外扩散。宿主若吞掉毒化信号并继续提供旧视图，就会重新引入框架拼命排除的幽灵。监督进程的职责因此包括：识别毒化、切断视图、安全 reopen、必要时告警人工。Durable 不是把运维变没了，而是把运维从「猜模型在干嘛」变成「处理明确的会话生命周期事件」。

    Chapter 9

    副作用三明治与重放

    任务步骤的标准形状是：提交意图 → 执行效果 → 提交结局。这叫副作用三明治。重开时若落在意图相位，含义是：效果可能已经发生。默认工具标 replay: "unsafe"：崩溃后不重跑，模型收到 interrupted。只有你标明 safe（且工具确实幂等）才会重跑。外部效果绝不回滚；模型请求「可能付两次钱」。

    子智能体在 Durable 里是模式而非独立 API：前台子智能体由调用方工具任务拥有；后台则用锚点任务加报告任务。费用账本 pi.usage 按对话记账，宿主若再按拥有关系粗加总，可能双计。试点时把账单对账列入验收，否则你会以为「模型变贵了」，其实是自己加了两遍。

    Chapter 12

    真正让 Durable 奏效的是什么（以及它不保证什么）

    到这里，机制已经铺开。值得停下来问一个 Wolfram 式的问题：既然只是「提交 + 任务状态机 + 单写者存储」，为什么它能支撑长跑智能体应用？哪些地方理论与工程其实还没保证完？

    奏效的部分

    若只记住营销句「能活过灾难」，你会买错保障。真正买到的是一套关于可见性的纪律，外加一套关于任务相位的词汇表。纪律让 UI 与存储对齐；词汇表让崩溃后的程序有话可说，而不是只有核心转储。

    第一，它把「可见」与「已提交」绑死。人类与多客户端之所以能一起转向同一个智能体，不是因为有了神奇的实时数据库，而是因为任何人看见的状态都有提交因果。晚到的观众拿快照；落后的观众被折叠到最新——产品可以粗糙，但不会长期活在谎言里。

    第二，副作用三明治把不确定性变成可叙述的运维事实。重开落在 intent，等于系统诚实地说：「我可能已经动过外部世界。」默认 unsafe 重放避免了盲目重做；safe 标记把责任推回给你——这正是该推回的地方。

    第三，任务与文档把「进行中工作」从内存幽灵提升为可调度对象。缺扩展代码时不假装成功终结，而是挡住并等待注册——升级滚动时，这比静默标失败更可运营。压缩是任务而不是隐形魔法；摘要竞争用 stale-head 规则裁决；每次摘要尝试都可能产生费用。手册还提醒：摘要请求会截断工具结果（约 2000 字符）；压缩期间的编辑可能丢失——这是 footgun，不是罕见边角。长对话试点要把「压缩发生时用户仍在写入」列入演练脚本。

    第四，库的体积与「几乎不在运行时检查脚枪」换来了可读性。博客称 Durable 大约一万五千行量级（不含测试）；不同清点方式给出一万七到一万九千行左右。[manual vs code] 行数口径不一，定性结论相同：小到一个团队可以读完。三十八条 API footgun 被写成合约而非「再加防御层」的邀请——这是显式的设计交易。

    不保证的部分（写进合同思维）

    它不保证外部副作用恰好一次。它不保证在 synchronous=NORMAL 的 SQLite 上掉电仍保住最新提交——「Durable」在此语境首先是进程崩溃耐久。它不提供跨进程锁、对话删除、流游标、自动第三方视图挂载、CRDT、JSONL 自动修复、或强制终止不合作扩展代码。它不识别用户；Cloudflare 侧也写明尚无工具审批步骤。规格仍写着 Pico5「尚未实现」——以代码为准，规格滞后。

    与 Temporal 一类通用耐久执行引擎相比，Pi Durable 是嵌入式库：没有集群要运维，保证也更弱（单进程）。与 LangGraph 的 checkpointer 相比，两者都仍需宿主检测失败并重启；Pi 把相位与检查点写进任务模型，并把「重开即续跑」放进 open() 路径，但监督责任仍在你。与 Claude Managed Agents 的内置权限策略相比，Pi 是模型无关且权限外置。这些不是优劣榜，而是原则对照：你买的是哪一种「真相来源」。

    为何有效（诚实版）。 因为智能体应用的核心痛点往往不是「模型不够聪明」，而是「崩溃后不知道世界与记忆谁先谁后」。Durable 强迫你把可见事实提交化，并把效果留在可叙述的不确定性里。它有效，是因为约束了谎言；它不够，是因为没替你约束外部世界。

    还可以用「负空间」理解设计：规格 §13 列出一整串故意不做的事——整 Session DOM、可见但非耐久的发布、语义事件杂志、自动检查点启发式、CRDT 多写合并、Chord op 的 SQL 翻译、JSONL 全局压缩或自动修复、强制杀死不合作扩展，等等。负空间不是懒，而是防止库重新长成你想逃离的那种全能运行时。公司若需要其中某一项，应在宿主层明确立项，而不是开 issue 期待内核「顺便做了」。

    三十八条 footgun 被描述为合约：几乎不在运行时检查。这意味着类型与测试要由你补。一致性套件存在的意义，就是把「自定义存储 / 自定义环境」从口号变成可回归的门禁。没有这道门禁，一次看似无害的 FileSystem 封装就能在升级后让 watch 语义漂移（1.0.4 已示范）。读完本章，若你只记住一句话，记住这句：Durable 用小核心换取你在边界上的工程成熟度。

    Interlude

    把机制翻译成验收问题

    在进入决策树之前，用一组可以写进试点验收的问题，把前面各章钉死。答不上来，就说明机制还没读透，清单分数没有意义。

    当进程在工具执行中被杀死时，你的存储里是否看得到工具意图？若看不到，你跑的是「会话耐久」还是「进行中耐久」？重开之后，默认是 interrupted 还是重跑？谁为重跑的双写负责？流式半截有没有进入提交？节流间隔是否按环境调整过？

    收件箱在忙碌时走 steer、followUp 还是 reject？幂等键落在 requestId 还是 Cloudflare 的 operationId？多人同时转向时，写者是不是仍然只有一个进程？权限扩展是强制配置，还是「文档里建议安装」？缺扩展名时，系统是失败鸣笛，还是静默跳过？

    存储后端选了哪一个？有没有两副本抢同一文件的路径？一致性套件是否进 CI？升级到含 Breaking 的 patch 时，谁跑套件？在 Cloudflare 上，单次模型流是否可能超过十五分钟？没有游标时，前端掉线重连的产品语义是什么？毒化 Session 的告警接到了哪里？

    这些问题故意不提供「标准答案」。它们的作用是暴露判断依据：若团队无法在白板上画出 intent→effect→outcome，并指出崩溃落点，那么 Durable 试点应从培训开始，而不是从接 Slack 开始。编码智能体路径同样有验收问题：沙箱是否强制、权限包是否不可卸、会话目录是否分级、遥测是否已核实载荷。

    最后用一段话收束机制阅读体验。智能体系统让人着迷的地方，常常是模型偶尔表现得「像懂了」。工程上真正决定能否上线的，却是另一些更无聊的问题：什么被写下了、什么只存在于内存、什么已经泄漏到外部世界、崩溃之后程序是否还诚实。Pi 编码智能体把无聊问题留给人类操作员；Pi Durable 把其中一部分变成提交与任务，但仍把外部世界的诚实留给你。公司若能分清这两层诚实，就不会在错误的层上寻找安全感。

    路径要点（判断依据暴露）

    下面每条路径都写出「为何此时可选」与「必须自建什么」。决策树互动控件会把你导向其中一条，但最终签字前，请回到第 6–9 章确认：你是否真的理解 intent 窗口与 unsafe 默认。不理解就上路径 3/4，等于在实验 API 上叠加语义债务。

    1. 路径 1 · 编码智能体。 托管安装或 Nix；标准化 settings.json（遥测、包允许列表、MCP）；容器 / Gondolin / Docker Sandboxes；内部 Pi package 发放权限扩展。盯：无默认权限弹窗；项目信任非沙箱；patch 级破坏性变更（如 Azure provider 重命名）；会话含密钥。

    3. 路径 3 · 自管 Durable。 SQLite + 每存储单进程监督；强制身份与 beforeTool 审批扩展；幂等工具标 safe；外部写做成带幂等键的任务（outbox 模式目前缺糖，维护者承认）；备份；pin 版本；CI 跑存储与 env 一致性套件。从 examples 00–31 与 vacation 演示起步。
    4. 路径 4 · Cloudflare PiHarness。 Agent + lifecycle.use(new PiHarness(...))；用入站事件 id 作 operationId。接受：实验库 + beta 适配器；15 分钟流上限；无审批；无事件游标；无删除。

    核心 MIT「forever」；未来可能有 Fair Source 增值与专有企业/云功能（尚未建成）。商标属 Earendil。Radius（early alpha）已接入 /login、/share、/bug。无 CLA/DCO。「数百万人每周」类用户数属营销表述，未核实；npm 周下载含 CI/传递依赖，不能当用户数。

    与竞品的原则对照（不是功能清单赛）

    Claude Code / Managed Agents 走厂商一体化：内置权限策略与托管运行时。Cursor 走 IDE 内嵌闭源体验。OpenAI Agents SDK 常借 Temporal 补耐久。LangGraph 用图与 checkpointer，节点恢复时常从头重跑，且仍需外部检测失败。Temporal 本身是通用耐久执行引擎，保证强、运维重。Cloudflare Agents 也可以不用 Pi，而用自研循环或 Project Think。Pi 的位置是：模型无关的小循环 +（可选）嵌入式提交化耐久库；治理与身份默认外置。选它，等于选「可读的核心 + 自建边界」；不选它，往往是因为你更想买边界而不是造边界。

    贡献模型也影响企业策略：新贡献者的 issue/PR 默认自动关闭、每日审阅。上游修复可能需要既有关系；计划里应预留 fork 或私有补丁分支。总线因子方面，项目属 VC 支持公司，关键决策集中；MIT 允许分叉，但商标与商业层（Radius、未来 Fair Source）仍由 Earendil 控制。这些不是拒绝理由，而是采购与架构评审必须写进纪要的句子。
