前言

前言一个循环与一条规则

智能体框架看上去复杂，内部却往往只有两件事。第一件是一个循环：把转写交给模型，执行模型要求的工具，把结果放回转写，再交给模型，直到模型不再要求工具为止。第二件是一种记账方式：在进程随时可能死亡的世界里，决定哪些事情必须先写下来，哪些事情可以等到以后再写。Pi 1.0 把第一件事做到了足够小，小到一个人可以读完它的核心；Pi Durable 把第二件事收敛成一句话：只有已提交的状态才可被观察。

这本书沿着这两条线展开。第一篇讲编码智能体 Pi 1.0：它的循环、会话树、工具与守卫、扩展与技能、Codemode 与 MCP、四种入口，以及它刻意不提供的东西。第二篇用一次真实的崩溃实验说明，为什么一个保存了对话的智能体在进程死亡时仍然会失去“那一轮”。第三篇进入 Pi Durable 的机制：四层结构、提交规则、十七次提交、任务与副作用三明治、收件箱、文档与分叉、注册表、存储与 Cloudflare 上的运行方式。第四篇是案例，其中一章完整记述 Elvis（@omarsar0）用 Pi Durable 搭建个人智能体 My Pi 的过程，并把他公开陈述的每一项能力对应到框架中的具体原语。第五篇回答两个问题：它为什么奏效，它不保证什么。第六篇面向准备采纳的公司。

书中的图分两类。一类重绘两本技术手册里的关键插图，例如编码智能体一次真实运行的事件序列，Pi Durable 在 kill -9 之后的存活情况、四层结构、十七次提交、任务状态机与副作用三明治；另一类是对照实验与计算器，读者可以拖动、切换、勾选，自己观察系统在每一步多出了什么状态。图注使用简化的技术英语风格，正文使用完整的论述。

第一篇

编码智能体 Pi 1.0

一个人、一个终端、一个循环。它刻意很小，所有其余的东西都由你加载的代码提供。

第 1 章智能体只是在运行一个循环

在终端里输入一个问题，按下回车，几秒钟之后得到一个回答，中间屏幕上滚过读文件、跑命令、改代码的记录。这个体验容易让人以为背后有一套复杂的规划系统。打开 Pi 的源码，会发现驱动这一切的是一个很短的循环：用户提示进入转写，转写交给模型，模型返回文字和若干工具调用，工具被执行，结果作为新的消息追加到转写，然后再一次交给模型。只要模型的回答里还有工具调用，这个循环就继续转；当模型只回答文字时，一次运行结束。

Pi 的作者把它描述为一个“极简、可扩展、你可以据为己有的智能体框架”。这句话首先是一条设计约束：核心只决定提示如何到达模型、工具如何运行、对话如何存储，其余决定几乎都交给你加载的代码。发布在 npm 上的 @earendil-works/pi-coding-agent 1.0.4 只安装一个可执行文件 pi。它背后是七个面：统一的大模型抽象层、智能体循环、会话运行时、工具、会话存储、扩展 API 与运行模式。默认激活的工具只有四个：read、bash、edit、write；另有 powershell、grep、find、ls 内置但默认不激活。

要理解一个循环在做什么，最好的办法是看它真实跑一次。Pi 技术手册用一个不联网的假模型（faux 提供方）驱动真实的 AgentSession：用户问“hello.txt 写了什么”，假模型第一次回答“Reading it.”并请求读文件，read 工具执行，假模型第二次回答文件内容。这次运行产生了 29 个会话事件、两次模型调用、四次写盘、八行 JSONL。下面的图把这次运行按事件顺序重放出来。

这幅图里有几件事值得放慢来看。第一，提示在到达模型之前已经落盘：第 6 个事件是用户消息的 message_end，会话文件在这一刻才被创建，此前暂存在内存里的五条记录（会话头、模型选择、思考级别、系统消息、用户消息）一次写入。第二，模型流式输出时产生的十个 message_update 事件只驱动界面重绘，不写盘；助手消息只有在完整结束时才成为文件里的一行。第三，第 28 个事件 agent_end 并不是终点。循环结束之后，AgentSession 还要检查是否有可重试的错误、是否需要压缩、是否有排队的消息，最后才发出 agent_settled，prompt() 在这一刻返回。一个只等待 agent_end 的客户端，会在系统还可能继续运行的时候误以为它已经空闲。

这一次运行之后，系统多了什么状态？磁盘上多了一个八行的 JSONL 文件，每一行的 parentId 指向上一行；内存里的智能体回到空闲；模型那边什么也没有留下，因为每一次请求都携带完整的上下文。整个状态都在那个文件里。这个事实决定了 Pi 的许多性质：会话可以被导出、分享、继续、分叉，也决定了它的局限：没有写进文件的东西，进程一死就不存在。第二篇会回到这一点。

循环之所以能这么小，是因为今天的模型已经“知道”编码智能体该怎样行事。给它一个能读文件、写文件、编辑文件、执行命令的工具集，它会自己决定先读什么、改哪里、跑哪个测试。框架的工作不是替模型规划，而是可靠地把模型的意图变成真实的调用，再把真实的结果交还给模型。Pi 把除此之外的东西都放到了核心之外。官网有一节题为“我们没有做的东西”，列出五项：子智能体、计划模式、权限弹窗、待办系统、后台 bash。

这五项留白各有一条明确的替代建议。子智能体：通过 tmux 启动多个 Pi 实例，或者用扩展自己写。权限弹窗：在容器里运行，或者自己写确认流程。计划模式：把计划写进文件。待办：在项目里放一个 Markdown 文件。后台 bash：用 tmux，“完全可观察、可直接交互”。仓库为前四项提供了参考扩展，后台 bash 没有。MCP 曾经也在这张清单上，1.0 起以内置扩展的形式出现，可以用 -builtin:mcp 移除。这一变化说明极简主义并非教条：当某个能力被足够多的人以几乎相同的方式重写时，它会进入默认配置，但仍然保持可替换。

把留白当作缺陷来看是一种误读。每一项留白都对应一个扩展接缝：权限门是一个返回阻断的 tool_call 处理器，计划模式是一个 before_agent_start 处理器加一条命令。要某个功能时，先找承载它的事件，再找仓库里最近的参考实现。这种做法的代价也很明确：凡是核心不做的，就由你来做，由你来维护，由你来承担它出错的后果。对个人开发者而言这是自由；对公司而言，这是一份工程与治理的清单。

第 2 章一个仓库，三个包构成一条链

“Pi”这个名字在不同语境下指不同的东西：一个品牌、一个仓库、一个命令行工具、一个 SDK，以及自 2026 年 10 月 1 日起的一个持久化框架。仓库 earendil-works/pi 采用 MIT 许可，是一个 TypeScript 单体仓库，含十四个包，全部处于 1.0.4。打开 packages/ 会看到十四个目录，却没有任何地图。

稳定的 pi 命令真正依赖的只有一条三包链：pi-coding-agent 依赖 pi-agent-core，后者依赖 pi-ai。命令行工具本身的代码量比它依赖的一切加起来还多，约占仓库的一半；而循环本身，即 pi-agent-core，只有两千余行，约占 1.4%。pi-ai 提供统一的多提供方大模型接口：手册在该提交计得 10 种对话线协议、42 家已知提供方，生成的模型目录共 1,620 条（1,537 条对话模型、60 条图像模型、23 条分类模型）。这个数字只说明“模型无关”在工程上意味着什么样的规模，不构成任何产品承诺。

另一组包服务于实验栈：pi-durable、chord、pi-env、pi-server、pi-client、pi-protocol。chord 是应用组合运行时，提供服务、复制状态、RPC 与插件；Pi Durable 用它跟踪文档。命令行工具在 devDependencies 里列了 client、protocol、server，src/experimental/ 下的二十个文件导入 pi-durable 却没有声明依赖，能解析只是因为根目录把所有包设为 npm 工作区。npm 包的 files 字段排除了实验目录，所以从 npm 安装 pi 不会带上任何实验代码。环境变量 PI_EXPERIMENTAL 必须严格等于字符串 "1" 才打开开关，true 或 yes 都不行；即便打开，从 npm 安装的二进制里也没有那些代码。

这条分界对阅读源码和评估风险都有用。一个经验法则是：如果你正在看的文件导入了 pi-durable、pi-server、pi-client、pi-protocol 或 chord，它就不在稳定命令的执行路径上。关心稳定命令，先读三包链；关心界面、MCP 或 Codemode，再读 pi-tui、pi-mcp 与 pi-codemode。所有包都声明 engines: node &gt;=22.19.0。

行数本身的口径也值得一提。Durable 的发布文章说它约一万五千行（不含测试）；研究测量约一万七千行（不含测试工具目录）；编码智能体手册按“src 下非空行、排除测试与生成目录”的口径计得 18,338 行。三个数字都对，只是边界不同。把任何一个当作权威，都会在别人用另一种口径复核时显得失真。本书在需要时只说“数万行量级，足以在一两周内读完”。

第 3 章一次运行要经过一串固定的关口

从按下回车到 prompt() 返回，编码智能体手册把一次运行拆成 22 个步骤并逐一对照源码核实。不必记住每一步，但值得知道它们分成几段，因为几乎每一个扩展点、每一种失败方式都落在其中某一段上。

第一段是提示管线。交互模式里，编辑器的提交处理器自己处理内置斜杠命令和以 ! 开头的 bash 行，其余文本交给 AgentSession.prompt()。这个方法按固定顺序执行：扩展命令运行并返回；输入处理器可以改写或消费文本；技能命令与提示模板展开；如果已有运行在进行，文本作为 steer 或 follow-up 入队，prompt() 立即返回；否则检查模型与认证、检查上一个回答是否需要压缩，再运行 before_agent_start 处理器，它们可以追加消息或替换系统提示。print、JSON 与 RPC 模式调用的是同一个方法。

第二段是交接与第一次写盘。系统提示是转写中的一条消息，而非请求里的一个字段；只有当系统提示的各个段落与转写中已有的不同时，才会在用户消息前插入新的系统消息。这样做的好处是提示缓存：不变的前缀保持不变。循环发出 agent_start 与 turn_start，为每条新消息成对发出开始与结束事件。AgentSession 收到每个事件后先交给扩展，再交给订阅者；在 message_end 时把消息追加到会话。

第三段是模型调用。每次请求前，循环调用 prepareRequest，AgentSession 用会话树的一个投影替换上下文，压缩摘要与上下文编辑正是在这个投影里生效。随后上下文经过 transformContext（在命令行中对应扩展的 context 事件）与格式转换，交给模型运行时；运行时解析提供方与凭证，用十种线协议之一发出 HTTP 请求。提供方返回的事件流先有 start，再有文本、思考与工具调用的增量，最后是 done 或 error；循环把它们分别转成消息开始、更新与结束事件。

第四段是工具批次。循环收集回答中的工具调用。默认并行执行；当智能体设置为顺序模式，或任一被调用的工具声明 executionMode: "sequential" 时，逐个执行。每个调用先发出开始事件、校验参数、运行 beforeToolCall，这会触发扩展的 tool_call 事件；处理器返回 { block: true } 时，调用直接变成错误结果，工具不运行。执行之后，afterToolCall 触发 tool_result 事件，处理器可以替换内容、细节或错误标志。结果消息落盘，轮次结束；因为回答里有工具调用，内层循环再转一圈。

第五段是收尾。第二个回答不再有工具调用，循环发出 agent_end。但 _runAgentPrompt 并不立即返回：它依次检查最后一个回答是否是可重试的错误、是否需要压缩、是否有排队消息，任何一项需要时都会调用 agent.continue() 再跑一次；最后 agent_before_settle 处理器还可以要求继续。只有这些都不需要时，finally 块才发出 agent_settled。

这五段之后，系统多出的状态都在会话文件里，而界面看到的是另一种东西：事件流。这两者的区别在后面会反复出现。事件是给观察者的，转瞬即逝；文件行是给未来的，永久保留。钩子 input、before_agent_start、context、tool_call、tool_result 与 agent_before_settle 只派发给扩展运行器，不出现在订阅者看到的 29 个事件里。所以要拦截行为，用扩展；要显示进度，订阅事件；要知道发生过什么，读文件。

对照实验：只等 agent_end 的客户端

事件与文件的区别，可以用一个小实验说明。设想一个通过 RPC 驱动 Pi 的客户端，它订阅事件，在收到 agent_end 时把界面标为“空闲”，并允许用户发出下一条提示。大多数时候它工作正常。但当最后一个回答是一个可重试的错误时，AgentSession 会在 agent_end 之后自动重试；当上下文接近上限时，它会先压缩；当运行期间有 follow-up 排队时，它会立即开始下一次运行。在这三种情况下，客户端认为空闲的那一刻，智能体其实还在工作，用户新发的提示会被当作 steer 或 follow-up 排入队列，而不是开始一次新的运行。

把判断条件换成 agent_settled，问题就消失了：只有在重试、压缩、排队消息与 agent_before_settle 处理器都不再要求继续之后，这个事件才会发出。手册特别强调了这个区别：空闲的客户端必须等待 agent_settled 或 prompt() 的解析。这个实验的意义不止于一个事件名：它说明观察者看到的“结束”与系统内部的“结束”可以不是同一件事，而让两者一致，是框架设计里最容易被低估的一项工作。第三篇会看到，Pi Durable 把这种一致性提升为一条硬性规则。

运行进行中输入的消息如何处理，也在这个循环里定义。交互界面上，回车发送一条 steer，它在当前工具轮结束后被注入，模型在下一轮就能看到；Alt+回车排入一条 follow-up，它等整个运行结束后才开始新一轮。两个队列都在内存里。这个细节在第二篇会变得重要：进程死亡时，排队中的消息随之消失。

第 4 章会话是一棵只追加的树

Pi 把会话存为 JSONL 文件，位于 ~/.pi/agent/sessions/&lt;cwd&gt;/ 下。文件的第一行是会话头，其余每一行是一个条目，每个条目都有 id 与 parentId。这让一个文件可以容纳一棵树：从任何一个较早的条目出发，都可以长出新的分支，而原有的分支仍在原处。

/tree 命令在同一个文件里移动“当前叶子”：回到更早的条目，从那里继续，离开的分支可以被总结成一段摘要，但不会被删除。/fork 从所选条目创建一个新的会话文件；/clone 复制一条分支；/export 写出 HTML 或 JSONL；/share 上传到私密 gist，登录 Radius 后则上传为 Radius 制品。这里有一个对公司很重要的事实：会话文件包含工具读到的一切，可能包括密钥、内部代码与客户数据。分享与导出都需要审查。

只追加的设计让“回到过去”变得廉价且安全：没有任何操作会改写已有的行。它同时带来一个问题：转写会一直变长，而模型的上下文窗口是有限的。Pi 的回答是压缩。当上下文 token 数超过上下文窗口减去预留量时，自动压缩被触发：较早的消息被总结成一段摘要，最近的消息原样保留。压缩改变的只是送给模型的那个投影，文件里的原始条目一条也不删除。

预留量的默认值是 16,384 个 token，与默认的高思考预算同值。可以这样理解两者的关系：预留空间需要容纳模型的下一次回答，其中包括它的思考过程。上下文溢出时，有一次“压缩后重试”的恢复；扩展可以通过 session_before_compact 等钩子参与压缩，例如保留某些不应被总结的内容。压缩发生在第 3 章所说的第五段（运行结束后检查是否需要压缩），也可以在轮次之间由 prepareNextTurn 触发。

会话树与压缩合在一起，构成了编码智能体的全部记忆模型：一棵永不删改的树，加上一个随时可以重新计算的投影。这个模型足够简单，人可以直接打开文件阅读；它也足够强大，支持分支探索、回退与总结。它唯一做不到的，是记录“正在发生的事情”。树里的每一个节点都是一条已经完成的消息。一个正在流式输出的回答、一个正在运行的工具、一条刚刚排入队列的 steer，都不是节点。

第 5 章工具调用先过守卫，再以你的身份执行

模型无法直接触碰世界。它能做的只是在回答里写下一个工具名与一组参数。把这段文字变成一次真实的文件写入或命令执行，是框架的工作；在变成真实调用之前有没有人或规则看一眼，也是框架的选择。Pi 的选择是：核心不问。安全文档的原话是“Pi does not ask approval per tool call”。

一次工具调用经过六个阶段：按名查找工具，按 schema 校验参数，触发 tool_call 扩展事件，执行，触发 tool_result 扩展事件，结果落盘。第三个阶段是唯一的接缝。仓库里的 permission-gate、protected-paths、confirm-destructive 示例都挂在这里：前者在调用匹配危险模式时弹出确认，第二个保护指定路径，第三个对破坏性操作要求确认。处理器返回阻断时，调用变成一条错误结果交给模型，模型可以据此改变策略；处理器自己抛出异常时，调用同样被阻断。这种“失败即阻断”的设计意味着守卫代码里的缺陷倾向于让系统更保守，而不是更危险。

但守卫只是策略，而不是隔离。被放行的调用在宿主进程里以你的身份运行：bash 能做的，模型就能做；你的环境变量、SSH 密钥、云凭证，模型都能间接触及。手册对内置工具的统计是 4 个默认激活加 4 个内置备用；它们都没有沙箱。所以第 9 章讨论的容器与微虚拟机不是可选的加固，而是公司使用时的基本条件。

工具执行默认并行。一个回答里若有多个工具调用，它们同时运行，一个失败不会取消其他。这对读文件这类只读操作是好事，对互相依赖的写操作则需要工具自己声明顺序执行。每个工具的结果在执行完后才成为文件中的一行；执行过程中的输出只在事件流里出现。

这一章之后，读者应当对 Pi 的安全姿态有一个清楚的图景：模型输出被视为不可信，提示注入在安全边界之外，扩展以完全权限在进程内运行，项目信任不是沙箱。这些都写在官方安全文档里，Pi 技术手册的 §7.2 以相同的威胁模型重述。没有任何新的矛盾，只是把责任明确地放在了使用者一侧。

第 6 章行为来自你加载的代码

Pi 的定制面有五层，按侵入程度从低到高依次是：上下文文件、提示模板、技能、包与扩展。理解它们的区别，比记住每一个 API 更重要，因为它们的风险完全不同。

上下文文件是最轻的一层。AGENTS.md 与 CLAUDE.md 会被读入系统提示，SYSTEM.md 可以替换系统提示。它们是文本，影响的是模型读到什么。提示模板是可复用的提示片段，以斜杠命令调用。技能遵循 agentskills.io 规范：每个技能有一段描述放进系统提示，模型需要时再读取完整内容，这叫渐进披露，目的是在不占满上下文的前提下让模型知道“有哪些能力可以调用”。这三层都只改变模型看到的文字。

包与扩展则是代码。扩展是用 jiti 加载的 TypeScript 模块，在 Pi 进程内运行，拥有完全权限。它可以订阅事件（pi.on），注册工具、命令、模型提供方、MCP 服务、虚拟模型与工具渲染器。手册在该提交计得扩展 API 有 41 个可订阅事件与 31 个方法；仓库附带 79 个扩展示例，从权限门、受保护路径、沙箱、Gondolin、计划模式、子智能体、git 检查点，到路由器、SSH 与小游戏；另有 14 个 SDK 示例。官网称“50 多个示例”，实际更多。

工具的暴露方式有多种：直接暴露给模型、只在 Codemode 中可达、延迟加载（由 tool_search 按需发现）或隐藏。延迟加载是 1.0 的新能力之一，配合 tool_search，模型可以在需要时才发现某个工具，避免一开始就把几十个工具的 schema 塞进上下文。1.0 的其他新能力包括 Codemode、原生 MCP、虚拟模型（路由器）、Anthropic 缓存预热、对话中途的系统消息，以及默认全屏的终端界面。

虚拟模型值得单独一提。它让一个“模型名”背后对应一段路由逻辑：选择与调度是分开的，扩展可以根据任务、成本或可用性把请求分派给不同的真实模型。对公司而言，这是在不修改工作流的前提下切换供应商、实施成本控制或灰度新模型的入口。

包把这些东西打成可分发的单元：pi install npm:…、pi install git:… 或本地路径。带 pi-package 关键字的 npm 包会出现在 pi.dev 的包库里。宿主包作为 peerDependencies 声明；项目级的包只在项目被信任之后加载。这一点是公司分发内部能力的标准做法：把公司的技能、提示模板与守卫扩展做成一个内部 Pi 包，由平台团队维护版本，开发者一条命令安装。

把五层放在一起看，可以得出一个简单的审查原则：文本层的风险是“模型被误导”，代码层的风险是“进程被接管”。前者靠容器与守卫兜底，后者只能靠代码审查与供应链控制。对一个来自第三方的 Pi 包，应当像对待任何一个 npm 依赖那样审查它，因为它就是一段在你的进程里以你的权限运行的代码。

第 7 章Codemode 与 MCP 把工具组合起来

当一个任务需要连续调用十几个工具，并在调用之间做一些计算时，逐个通过模型往返既慢又贵。Codemode 的思路是让模型写一段 JavaScript，在沙箱里一次跑完。这段代码作为 async 函数体在 QuickJS（编译为 WebAssembly）中运行。沙箱里没有 Node API、没有文件系统、没有网络、没有定时器，唯一的对外能力是通过 tools.* 调用被注入的工具，通过 models.* 调用非对话类模型。

沙箱的边界常被误读。它限制的是脚本“能做什么”：脚本不能绕过工具直接读写文件或发网络请求。它不限制工具本身做什么：脚本调用 tools.bash，bash 就在宿主上真实执行。文档写得很直白：工具调用是真实的，失败之前已做的调用不会被撤销。所以 Codemode 并不改变第 5 章的安全结论；它只是把多个调用打包成一次模型往返。

脚本可以用 store() 与 load() 保存少量状态。这些状态被写成会话条目，因此会随分支移动：在 /tree 回到较早的条目后，load() 读到的是那条分支上的值。这是一个小而精确的设计：脚本状态与对话状态共享同一套历史语义。

MCP（模型上下文协议）在 1.0 中成为内置能力，支持 stdio 与 Streamable HTTP 两种传输，支持 OAuth（含 RFC 9207 发行者校验与客户端 ID 元数据文档）。用户级配置在 ~/.pi/agent/mcp.json，项目级配置在 .pi/mcp.json，后者只在项目被信任之后读取。MCP 工具可以直接暴露给模型，也可以只在 Codemode 中可达。命令行默认启用 Codemode、tool_search 与 MCP；SDK 默认不启用，需要显式开启。这是一个刻意的区别：命令行面向个人使用，追求开箱即用；SDK 面向嵌入，追求“什么都不做，除非你要求”。

2026 年 6 月的一期播客里，作者仍以“没有 MCP”作为 Pi 的特点之一；四个月后，1.0 内置了 MCP、Codemode、tool_search 与虚拟模型。核心在长大。对于评估长期维护成本的团队，这是一个需要持续观察的信号：极简是方向，而非冻结的状态。

第 8 章四个入口共享同一个循环

Pi 有四种运行模式：交互式终端界面、print/JSON、RPC 与 SDK。前三种由同一个可执行文件根据参数选择：--mode rpc 或 --mode json 显式指定，-p 或标准输入输出不是终端时进入 print，否则进入交互界面。SDK 是第四条路：在你自己的进程里调用 createAgentSession()。

交互界面是大多数人认识 Pi 的方式，1.0 起默认全屏。print 模式适合脚本与 CI：输入一次，结果以文本或 JSON 事件流输出到标准输出。RPC 模式用标准输入输出传递 JSONL，严格以 LF 分帧，以 id 关联请求与响应；仓库提供 TypeScript 的 RpcClient 与一个 Python 示例。任何语言都可以通过 RPC 驱动 Pi，而 Pi 进程本身成为一个隔离单位：它崩溃不会带走宿主，它的权限可以被操作系统单独限制。

SDK 让循环嵌入 Node 或 Bun 进程。createAgentSession() 返回会话，AgentSessionRuntime 管理运行时，SessionManager 可以是持久的也可以只在内存中；模型运行时、设置管理器、会话管理器、资源加载器与工具都是可替换的边界。这让 SDK 成为构建内部工具的基础：CI 机器人、内部命令行、IDE 或聊天前端。

选择 RPC 还是 SDK，本质是一个取舍。RPC 换来语言无关与进程隔离，代价是序列化开销与对内部细节较少的控制；SDK 换来完全的控制与零序列化，代价是 Pi 与你的代码共享一个进程、一个崩溃域、一套权限。无论选哪条路，会话都还是 JSONL，运行中的工作都没有持久性。OpenClaw 用 SDK 嵌入 Pi 构建了一个大型产品，后来迁移到自己的运行时，第四篇会简要回顾这段历史。

第 9 章信任设置不是沙箱

在一个陌生的仓库里启动 Pi，会遇到项目信任的提示。理解它管什么、不管什么，是安全使用 Pi 的第一步。

信任决定的是加载哪些代码与配置。项目级的 Pi 包、.pi/mcp.json 里的 MCP 服务、项目扩展与技能，只有在项目被信任后才加载。但 AGENTS.md 与 CLAUDE.md 无论是否信任都会加载，模型因此会读到仓库里写的指令文本。一个恶意仓库可以在 AGENTS.md 里写下诱导性的指令；这属于提示注入，安全文档明确把它放在安全边界之外。对尚未阅读其指令文件的仓库，可以先用 -nc 启动。

信任也不决定模型能做什么。即使项目不被信任，模型仍然通过 bash 以你的权限执行命令。因此隔离必须发生在 Pi 之外。容器化文档比较了四种方法，示例扩展又补充了两种，它们把不同的东西放进边界之内。

只有整进程隔离能把扩展也关进去：Docker、Docker Sandboxes 或 OpenShell 中运行的 Pi，连同它的所有工具、! 命令与扩展，只能触及你授予的挂载、环境变量与网络。Gondolin 扩展把七个文件与命令工具移进微虚拟机，工作目录以读写方式挂载在 /workspace，但 Pi 本身、其他扩展的工具与宿主环境变量留在外面。sandbox 扩展只把 bash 放进操作系统沙箱。tool_call 守卫则根本不是边界。

几个细节决定了隔离是否真的有效。用 -e 传入的环境变量在容器内可见；把宿主的 ~/.pi/agent 挂进容器会暴露其中的凭证；Docker Sandboxes 的代理会把真实的提供方密钥替换为占位符，这是它相比普通容器的一个优点。供应链方面，仓库对直接依赖锁定版本，使用 min-release-age=2、--ignore-scripts 与 npm audit signatures；托管安装器（curl -fsSL https://pi.dev/install.sh | sh）会锁定传递依赖，而自 1.0.1 起，通过 npm 全局安装不再锁定传递依赖，因为 shrinkwrap 被移除了。对于成规模部署，托管安装器或 nix run github:earendil-works/pi/stable 更可控。

第一篇到此为止。编码智能体是一个可靠的循环加一棵只追加的树，外加一个开放到几乎任意程度的扩展面。它为一个人在一个终端里工作而设计。Durable 的发布文章把这个范围说得很清楚：编码智能体运行在你的（远程）机器上，在终端里，由一个人驱动；如果进程死了，你看看发生了什么，再告诉它继续。下一篇讨论的，正是“告诉它继续”这件事在无人值守时为什么做不到。

第二篇

为何需要 Durable

进程会在任意一条指令处死去。保存了对话的智能体，仍然会在那一刻失去正在进行的那一轮。

第 10 章杀死一个进程，看看留下了什么

讨论持久性，最有说服力的方式是做一次实验。Pi Durable 技术手册附带的捕获脚本做了这样一件事：在同一个 SQLite 文件里开两段对话，每段对话让模型调用一个慢工具，每个工具分十步打印进度；在两个工具都打印到第六步时，对进程 A 发送 SIGKILL；然后启动进程 B，打开同一个文件，看看它找到了什么、做了什么。两个工具唯一的区别是重放策略：会话 1 的 deploy 没有声明 replay，因而按默认值视为 unsafe；会话 7 的 fetch_report 声明了 replay "safe"。

实验的结果可以按时间读成三段。崩溃之前，两个工具在执行前各自提交了意图：阶段 execute、最终参数、重放策略。随后每打印一行，就有一次进度提交，最快每 100 毫秒一次，于是存储里有两段各六行的输出。崩溃那一刻，进程 A 没有机会做任何清理；最后一次提交之后的一切都不存在了。崩溃之后，进程 B 仅仅打开文件，就写下了一次提交：把仍处于 running 的任务改回 pending。这意味着打开本身是一次写入，监控面板不能“只是打开”一个正在被别的进程使用的存储。

恢复时，两个工具走向不同的结局。deploy 的存储策略是 unsafe，系统不会重跑它，而是写下一条结果：把已提交的六行输出原样交给模型，并附上一句“工具 deploy 被中断，可能已部分执行”，标记为错误。模型读到这条结果，如实回答部署失败。fetch_report 的存储策略与当前注册的策略都是 safe，系统先清空它的旧输出，然后在进程 B 里从第一步重新跑完全部十步，正常完成。两个输入最终都结算为 done。

这个实验里最重要的不是“恢复了”，而是“没有猜”。进程 B 没有试图推断 deploy 是否真的部署了一半，也没有因为不确定而放弃。它读到一个检查点，检查点说“这个副作用可能已经发生”，然后执行一个事先选好的策略。对 deploy 来说，正确的策略是如实告知；对 fetch_report 这种重跑无害的读取来说，正确的策略是重跑。框架的贡献在于把这个选择从崩溃之后的猜测，提前到了写工具时的声明。

同样的实验放到编码智能体上，结果完全不同。

一次轮回在进行中携带四类状态：转写，也就是到目前为止的消息；模型调用，一个流到一半的回答；工具调用，一个做到一半的副作用；应用状态，例如工具正在更新的待办列表。它们分别住在不同的地方，崩溃之后彼此不一致，而且没有任何地方记录每一类走到了哪里。编码智能体只保存第一类，而且只保存完整的消息。半截回答不在文件里，工具开始执行这件事也不在文件里，扩展在内存里持有的状态全部消失。

第 11 章保住了对话，保不住那一轮

编码智能体的会话设计在第 4 章已经介绍过：每条完整消息追加一行，形成一棵树。手册对它的评价很精确：这个设计保住了对话，却保不住那一轮。如果进程在工具运行时死去，文件就结束在调用这个工具的那条助手消息上。没有一行说工具已经开始，没有一行记录它打印了什么。下一个进程能把对话读回来，却无法判断那个工具的副作用有没有发生。

对一个坐在终端前的人来说，并不构成问题。进程死了，他看一眼终端里滚过的输出，检查一下部署状态，然后告诉智能体“继续，部署已经完成了一半”。人承担了恢复所需的全部判断。Durable 的发布文章正是从这里出发：编码智能体为“一个人、一台机器、一个终端”而设计，这个范围之内，人就是持久层。

一旦离开这个范围，问题就变得尖锐。一个在 Slack 里回答值班问题的机器人，没有人盯着它的终端；一个按计划每天早上运行的智能体，崩溃时所有人都在睡觉；一个运行数小时的调查任务，可能在中途因为部署、内存不足或笔记本合盖而被杀死；一个部署在 Kubernetes 上的智能体，随时可能因为 Pod 被驱逐而换一台机器继续。在这些场景里，没有人能替系统回答“刚才做到哪了”。

具体缺什么，可以逐项列出来。排队的消息只在内存里：用户在运行中发出的 steer 与 follow-up，进程一死就没了。半截回答不持久：一个已经流出几千个 token 的回答，重启后从头开始，而且这次请求可能再次计费。工具的开始没有记录：重启后无法区分“还没调用”和“调用到一半”。应用状态与转写分离：扩展在内存里维护的待办列表，崩溃后可能领先或落后于转写。没有单写者保证：两个进程同时打开一个会话文件，没有任何东西阻止它们交错写入。

社区里已经有人用别的方式补上这些缺口。一位 Hacker News 用户提到，他曾用 DBOS 在 Kubernetes 上为 Pi 会话提供存活能力，后来改用 Pi Durable。这类做法的共同点是：把持久性放在框架之外，用一个通用的工作流引擎包住智能体。它们能解决“进程死了重新开始”的问题，却很难解决“工具做到一半”的问题，因为外部引擎看不到框架内部的阶段划分。

Pi Durable 的回答是把持久性做进框架的记账方式本身。它做了三件事，每一件对应上面的一个缺口。第一，凡是可见的都先提交：对话、模型轮次、工具调用以及你自己的状态，在显示之前都写入存储；半截回答与工具的运行输出也被提交，进度提交之间默认至少间隔 100 毫秒。第二，工作是带检查点的任务：模型调用与工具调用各自作为一个任务运行，任务在每一步提交检查点；工具任务在执行之前提交意图。第三，应用状态是同一次提交里的文档：文档是存放在转写旁边的类型化 JSON，与条目在同一次原子提交中变化，所以待办列表永远不会领先于改变它的那条消息。

它刻意不做的事情同样重要。一个存储同一时间只能被一个进程拥有，没有跨进程锁，监督与重启是宿主的工作。没有多写者合并，许多客户端可以观察并引导同一段对话，但每一次写入都经过同一个 Harness。不回滚世界：提交只在存储内是原子的，外部副作用不在变更事务中运行。当框架无法知道一笔付款是否已经完成时，它会如实说出来，把答案留给幂等键或远端记录。第三篇逐一展开这些机制。

第三篇

Durable 的机制

一条规则，四层结构，五种记录，以及让崩溃变成暂停的那些细节。

第 12 章四层结构，一条变更线

Pi Durable 是一个库，而不是服务、产品、界面、认证层或权限系统。安装它只需要三个包：npm install @earendil-works/pi-durable @earendil-works/pi-ai @earendil-works/chord。它的形状可以看成一个四层的栈：你的程序请求 Harness 做事，Harness 把每个请求变成一次提交，提交经过唯一的 Session 内核，内核把它写入唯一的存储。

最底层是存储：一个保存记录与文档、并能原子地提交一批写入的后端。包内附带三种：内存、SQLite 与 JSONL。往上是 Session 内核，规范对它的定义是“拥有一条变更线、会话、条目、任务、提交与文档”。变更线是一个队列，一次只执行一个提交；内核还为每个已加载的文档保持一个跟踪器，并在每次提交之后通知观察者。内核可以单独使用，包内示例 00 到 05 就是这样做的。

再往上是 Harness：在内核之上加了会话句柄与注册表。它由四个组件构成。会话句柄本身不持有任何状态，一个句柄只是一个 id 加上一组方法，README 的建议是“按 id 比较句柄”。提交组件负责输入与写入的准入、每个会话的收件箱，以及 wait() 背后的等待者。任务调度器维护所有存活任务的内存镜像，负责预留、运行与中止它们。视图组件提供 viewState()、watch()、任务图与智能体事件。

Harness 用三个内置任务回答输入：pi.generation 准备提示并调用模型，pi.tool 执行一次工具调用，pi.compaction 总结旧上下文。它们不是扩展，不能被移除或替换；所以注册表必须从 createRegistry() 开始构建，Harness.open() 会拒绝一个缺少它们的注册表。其余的东西由宿主在打开时注入：models 是 pi-ai 的模型接口，生成任务通过它调用 streamSimple()；registry 是已安装的扩展；settings 是运行策略，每次使用时读取、从不存储；env 为每次工具调用与提示渲染构建执行环境；conversationCreated 在每次创建或分叉会话的提交中运行；now 是时钟，onReport 接收框架报告但能承受的错误。

跟随一次 root.submit(input, context) 穿过这几层，可以看清分工。会话句柄把输入交给提交组件；提交组件做一次提交，在这次提交里追加用户条目、记录提交、创建第一个生成任务，并在 pi.live 文档中把会话标记为忙；Session 把这次提交写入存储，然后才通知监听者；调度器是监听者之一，它看到新任务，用另一次提交把它认领为运行；任务在任何提交之外运行，通过 models 调用模型，每一个想保留的结果都作为新的提交回来。没有一层绕过另一层，调度器也只从已发布的提交中得知新工作。

这种分工的关键在于内存与存储的划分。存储持有真相；内存持有一个随时可以从存储重建的工作集：存活任务的镜像、已加载文档的缓存、等待者与订阅。进程死去时，这些都不重要，下一次 open() 会把它们读回来。README 的说法是“重新打开存储，工作就从停下的地方继续”。对宿主代码而言，这意味着三条纪律：你的代码只与 Harness 及其句柄对话，从不直接碰存储；重启之后需要的任何东西都必须在某次提交里，内存只是缓存；句柄不持有状态，重启后用 harness.conversation(id, context) 重新取得。

最小的宿主程序

一个能运行的最小宿主，只需要做五件事。第一，准备模型：创建 pi-ai 的模型集合，设置一个提供方；测试时可以用不联网的 faux 提供方，让它总是回答“Paris.”。第二，准备注册表：用 createRegistry() 创建，它已经带着三个内置任务。第三，打开 Harness：把一个存储（例如 openNodeSqliteStorage(path) 打开的 SQLite 文件）、模型与注册表交给 Harness.open()，同时传入一个 Chord 上下文，它只携带取消信号。第四，取得根会话并提交：harness.root() 返回根会话，首次调用时可以同时写入智能体配置，例如模型选择；对它 submit 一条带 requestId 的输入，再 wait 这条提交，直到它的状态成为 done。第五，关闭：harness.close()。

这个程序跑完之后，SQLite 文件里有一个会话、五个内置文档、一条用户条目、一条已结算的提交、若干个已结束的任务和一条回答条目。再次运行同一个程序，用同一个 requestId 提交，得到的是保存下来的那条提交，而不是第二次询问模型。关闭之后重新打开存储、取得根会话、按页读取条目，就能找到那条回答。手册把这个程序放在全书开头，用来验证存储与重开；它不模拟工具副作用中途的崩溃，那是第 10 章实验的任务。需要注意的是，内存存储只把一切放在内存里，示例中常用它写简短片段；想要重开已保存的工作，必须用持久后端。恢复未完成的工作之前，要重新安装相同的扩展与任务代码。手册的这个示例钉在 1.0.3 并在该构建上测试；本书正文锚定 1.0.4，两版之间涉及的差异见第 20 章。

包对外暴露十个导入路径：主入口提供 Harness、注册表与各种 define 函数、内置文档与任务、内存存储与 createSession；SQLite 与 JSONL 各有一个 Node 专用路径与一个可移植核心路径；内存存储单独一个路径；执行环境的接口与 Node 实现各一个；/tools 提供 read、write、edit、bash 工具与组合它们的 CodingTools 扩展；/testing 提供存储与环境的一致性测试和存储基准。十个导入路径就是十个可能在补丁版本中变化的面，采纳者应当把它们都视为不稳定的 API。

第 13 章只有已提交的才可被观察

整个设计可以压缩成一个想法：在提交之前，一切都不算数。提交是一次原子保存，里面的东西要么全部存下，要么一样都不存。屏幕上显示的东西，崩溃就拿不走。规范在任何类型定义之前，用两句话陈述了整个系统：Session 原子地提交不可变条目、完整的任务记录与 Chord 跟踪的文档；只有已提交的状态可被观察。

第一句说一次提交装什么：转写记录、任务记录与文档变更，作为一个单元写入。第二句说除此之外什么也看不见：屏幕、等待者、订阅，乃至调度器本身，都只读已提交的状态，没有侧信道。可以把它读成一扇门：每一个变化都经过提交，每一个观察者都站在门后。提交在变更线上依次经过回调、准备、存储、采纳与发布五个阶段；变更线从回调开始一直被持有到发布结束。副作用，即模型请求、工具与进程，在线外运行，它们的结果只能以新提交的形式回到门内。

规范 §1 随后列出八条“必需的不变量”。每一条都堵住一种具体的失败，下面的图可以逐条切换。

第一条，原子性跨越所有记录与文档写入。在单轮捕获中，第 6 次提交同时写入带工具调用的助手条目、把生成任务改为等待、创建工具任务、更新两个文档。如果拆成两次写入，崩溃恰好发生在中间，就会留下一个没有任何任务去执行的工具调用。第二条与第三条，先存储再发布，且只能如此。Session 只在 Storage.commit() 返回、新修订被采纳之后发布一次提交；第三条排除了替代方案：没有办法不提交就显示。所以部分回答与工具输出也必须被提交，节流由 settings.progress 控制。每一次这样的提交都是一次存储写入，这是“屏幕永远不显示崩溃能拿走的东西”的代价。

第四条，副作用不上线。所有会话共享一条变更线，如果在提交里等待模型调用，所有其他提交都会被阻塞到它返回为止；更糟的是，提交的内容会依赖一个它无法撤销的副作用。工具任务展示了正确的模式：提交意图，在线外运行 execute()，再提交结果。第五条，条目不可变，ID 永不复用。所有记录类型共享一个 ID 空间。

记录通过 ID 互相指向：工具任务 12 的输入是“助手条目 11 中的 call-1”，提交 8 的答案是条目 15。如果 ID 可以复用或条目可以改写，这些指针会悄悄改变含义。即使一个 ID 被一次失败的提交占用，它也保持已用状态。

第六条，草稿随回调一起死去。在提交内部，tx.doc() 返回一个可变草稿；回调结束时，Session 同步地准备或中止每一个打开的变更，草稿被吊销。测试会故意在提交之后保留一个草稿的引用，然后检查读写它都会抛错。没有这一条，一个游离的引用就能在任何提交之外改变文档。第七条，变更线覆盖存储与采纳。线一直被持有到存储结算、新修订被采纳，因此下一次提交总是从上一次存储的状态开始。提交观察者在线上运行，但只用于捕获不可变值；你的 watch 与文档状态回调稍后在线外运行，慢界面拖不住框架。

第八条，不确定的失败会毒化 Session。一个可能已经写了一部分的存储错误，让内存无法知道磁盘上有什么。此时 Session 拒绝之后的所有调用，提示它已被一次存储准入之后的失败提交毒化，需要重新打开。只有 StorageRejected 承诺什么也没写，只有它允许 Session 继续。准备阶段的失败，例如草稿里有一个非 JSON 值，发生在存储看到这批写入之前，会正常回滚。

对任何设计，这一章给出一个可以反复使用的问题：你显示的或据以行动的状态，已经提交了吗？如果没有，它还不存在。相关的东西放在一次提交里改，崩溃就永远不会把它们分开。永远不要在提交回调里调用模型、工具或网络。如果存储以一种可能已经写入的方式失败了，关闭并重新打开，不要重试。

当提交本身失败

规则说只有已提交的才可见，那么提交本身失败时会怎样？答案取决于失败发生在哪里。一次提交可能在五个位置失败：回调、结算、准备、存储与采纳；每一种失败都落入三种结局之一：回滚、被存储拒绝，或毒化。

前三个位置在存储之前。回调里你自己的代码抛错、一个 tx 操作被拒绝、先写表再读表触发的 ReadAfterWrite、草稿里出现非 JSON 值、引用一个不存在的会话或任务，这些都会让所有变更被丢弃、原始错误被重新抛出。回滚是完整的：什么也没存储，什么也没发布，每个文档保持原值，下一次提交正常运行。唯一的痕迹是 ID 序列里的一个空缺，因为被占用的 ID 不会再发放。在任务内部，一次回滚的提交通常会结束任务：阶段处理器让错误逃逸，任务以 faulted 结束。

批次一旦交给 Storage.commit()，Session 就不能再假设任何事情。存储契约定义了唯一安全的例外：StorageRejected 表示批次在产生任何持久效果之前被拒绝，保证没有提交，Session 像回滚一样处理它。后端只在能证明没有效果时使用它，例如 SQLite 报告一次失败的分叉拷贝。其他任何存储错误都会毒化 Session；存储成功之后、内存采纳新值时发生的失败也会，因为此时存储里有一次内存没有反映的提交。被毒化的 Session 拒绝一切需要它状态的操作，每一次提交、快照、状态读取与订阅都抛出同一个错误，并以原始错误为原因。失败的批次什么也不发布，所以没有任何观察者见过一个可能不存在的值。

还有一个容易踩中的陷阱：在回调里启动、却没有等待的工作，在事务结算之后仍可能试图改变它，然后失败。规范把这种“发出即忘”称为不受支持。每一个 tx 调用都要 await；后台工作只在 commit() 解析之后启动。对表的读取要先于写入，文档则可以在任何时候读写；回调要短，不做任何 I/O；草稿里只放 JSON，回调结束后绝不保留草稿；对变化的反应写在 watch 里，而不是提交观察者里。

第 14 章读完十七次提交，就读完了整个框架

一个用户问“数到 3”，模型调用一个计数工具，然后回答。这么小的一次交换需要十七次提交。按顺序读一遍，就能读懂任何一份提交日志：每一行是谁写的、为什么写、此刻崩溃会留下什么。

前两次提交建立会话与输入。root() 在提交 1 中创建根会话，同一次提交创建它的五个内置文档，ID 为 2 到 6：pi.live、pi.inbox、pi.usage、pi.provider 与 pi.agent，其中智能体文档保存了模型选择。打开 Harness 时也运行了一次提交，用于把运行中的任务调和回待定，但它什么也没写；没有写入的提交被丢弃，不占用序列号。submit() 是提交 2，正是它让输入变得持久。会话空闲，所以准入在一次提交中做三件事：追加用户条目 7；创建提交 8，状态 placed；启动一次运行，即创建生成任务 9，并把 pi.live.run 设为“任务 9、输入 [8]”。从这一刻起会话是忙的，因为“忙”的定义就是 pi.live.run 存在。此后崩溃不会丢失用户输入的任何内容；用同一个 requestId 重新提交，会返回提交 8 而不是创建新的。

提交 3 到 6 是第一次生成。提交 3 是调度器在工作：它把任务 9 从 pending 改写为 running 来预留它，检查点不变，仍是“阶段 prepare、第 1 次尝试”。这次运行里的每个任务都以这样一次预留提交开始。prepare 阶段渲染系统提示与工具表，作为系统条目 10 提交；同一次提交 4 把任务推进到 request 阶段，记下模型、思考级别与上下文截止点。request 阶段先提交 pi.live.generation = {attempt: 1}（提交 5），然后在线外调用模型。假模型的流在 100 毫秒节流窗口内结束，所以没有部分回答被提交；真实的、较慢的流会在这里插入若干次节流的部分回答提交。

回答以 toolUse 结束。提交 6 是这一轮的枢纽：它把回答写为助手条目 11，把用量加入 pi.usage，创建由任务 9 拥有的工具任务 12，在 pi.live.tools 中列出这个调用，并把任务 9 改为等待 [12]，策略为 allSettled。在提交 6 之后崩溃，重开时调用已记录、任务待定，工具会被执行；在它之前崩溃，重开时任务 9 仍在 request 阶段，模型调用就再做一次。后者意味着一次可能的重复计费，这是“中断的模型请求可能被付费两次”的具体来源。

提交 7 与 8 是意图先于副作用。提交 7 预留任务 12。它的 call 阶段从条目 11 读取调用、解析工具、校验参数、运行所有 beforeTool 钩子，然后在运行任何工具代码之前提交意图，即提交 8：阶段 execute，参数 {n: 3}，重放策略 unsafe（计数工具没有声明 replay）。这条记录是崩溃在工具中途可恢复的原因。execute 阶段只有在恢复时才会被单独到达；如果后来的进程发现一个任务处于这个阶段，工具就可能已经运行过，存储的重放策略决定是重跑还是写下中断错误。

提交 9 到 11 是输出与结果。工具的输出作为进度提交，默认最小间隔 100 毫秒：提交 9 把 pi.live.tools[0].output 设为“1”，提交 10 追加“2、3”。观察者看到输出在增长；崩溃只会丢失最后一次成功进度提交之后的输出，这个间隔没有固定上限。execute() 返回后，提交 11 追加工具结果条目 13，并把任务 12 结束为 completed，结果指向条目 13。

提交 12 到 17 是第二次生成与回答。任务 12 结束，任务 9 的等待结束。提交 12 在 tools 阶段预留任务 9；运行中排队的写入与 steer 就在这个阶段落地。然后它交出运行：提交 13 创建生成任务 14，把 pi.live.run.taskId 改为 14，清除工具轮，并把任务 9 结束为 completed。运行的“锁”在这里被交接，而不是先释放再获取，所以中间没有任何时刻会话看起来是空闲的。生成 14 重复第一次生成的阶段，只有一处不同：它的 prepare 阶段发现提示与工具没有变化，因此不追加系统条目，提交 15 只是把任务推进到 request。系统条目是位置增量，只在变化时发送。提交 16 在 pi.live 中标记尝试，模型以 stop 作答。

提交 17 一次完成所有收尾：追加回答条目 15，把提交 8 结算为 done、答案 15，把任务 14 结束，删除 pi.live.run 与 pi.live.generation 使会话重新空闲，并把第二次回答的 token 加入 pi.usage。提交组件在这次提交的发布中看到已结算的记录，解析宿主的 wait()。JSONL 后端跑同样的场景，也是十七次提交。

读完这张表，会注意到三条规律。用户的文字从提交 2 起就安全了。工具的意图在任何工具代码运行之前已经提交，所以恢复总是知道一个调用可能已经开始。没有任何一次提交会留下“有回答但提交未结算”或“有工具调用但没有任务”的状态。在任何一行之后杀死进程，重开时它都知道下一步该做什么。

第 15 章工作被切成带检查点的阶段

假设智能体正在为一笔订单扣款，笔记本合上了。进程回来时，必须有某样东西说明它做到了哪一步。在 Pi Durable 里，这样东西是任务。任务是一个被切成阶段的工作单元，Harness 边做边提交。每个阶段完成自己的部分后，提交一个检查点：一个小的 JSON 值，指明下一个阶段并携带它需要的一切。进程死后，下一个进程读取最后一个检查点，把那个阶段再跑一遍。除此之外什么也不会延续：变量与闭包都消失了，只有存储的记录留下。

框架自己的模型调用、工具调用与压缩都以这种方式运行。你用 defineTask() 编写任务，在扩展的 tasks 列表中注册它；Harness 每次启动任务时按名字查找代码。一个任务定义包括：name，即任务的种类，写入每一条记录，改名会让旧名字的存储任务搁浅；version，同样写入每条记录，新定义必须迁移旧记录；initial(input)，创建任务时提交的第一个检查点；phases，每个阶段名一个处理器；abort，中止后运行，必须提交一个最终结局；可选的 migrate 与 hooks。

任务总是处于五种状态之一。三种是存活的：pending 表示等待轮到它，running 表示代码正在执行它，waiting 表示暂停直到其他任务结束。另两种持有结局：completing 表示结局已定但它启动的工作仍在运行，terminal 表示永久结束，记录成为一张回执。你的代码只通过 runtime.commit() 移动任务：一个阶段可以提交新检查点并保持运行，开始一次等待，或以 terminal 结束。它永远不能设置 pending，只有 Harness 在崩溃后重开或把任务交给新加载的代码时才这样做。故障、孤儿与中止标记也由 Harness 写入。

任务的全部状态存在一条 JSON 记录里，每次提交整体替换这条记录。记录包括状态（存活时带检查点，结束后带结局）、等待的任务与策略、memo（先写者胜的小存储值）、持久的中止标志，以及仅子任务才有的 owner。conversationId 与 owner 永不改变。任务结束时，记录缩成回执：检查点与 memo 被丢弃，只保留结局。终态记录永久保留，所以结果要小；大数据放进条目或文档，只返回它的 ID。结局有五种：completed 与 failed 由任务自己写，aborted 由它的中止处理器写，orphaned 与 faulted 由 Harness 写。所有错误都是纯 JSON，从不是运行时的 Error 对象。

一个任务启动时，Harness 创建一次调用：任务在内存中的一次运行，带有自己的中止信号。调用一个阶段接一个阶段地运行，直到任务结束、等待或被停止。提交检查点并不结束调用，下一个阶段立刻在同一进程里开始。在每个阶段之前，Harness 运行一个“步”：一次读取已提交记录并决定是否继续的简短检查。步本身是变更线上的一次提交，因此能看到阶段返回之前做出的每一次提交。

六条规则按序匹配。已提交结局或等待：停止。Harness 正在关闭：停止，检查点与中止标记留给下一个进程，关闭从不写结局。有中止标记：停止本次运行，稍后在任务自己的子工作结束后另起一次中止运行。阶段抛出异常：写入 faulted。检查点已变化：继续下一阶段，或把任务交给新加载的代码。检查点未变化：写入 faulted，因为没有取得持久进展。顺序在两种情况下要紧：先提交新检查点再抛错，仍然 faulted，因为规则 4 先于规则 5；先提交最终结局再抛错，结局保留，因为规则 1 最先。

“无进展即故障”这条规则看似严厉，其实是必要的。一个以开始时的检查点结束的阶段，会以相同的输入再跑一次，永远如此。所以步把两个检查点按 JSON 比较（忽略键顺序），相等就判故障。三种写法会踩中它：阶段什么也不提交就返回；阶段提交了条目或文档，但 runtime.commit() 没有返回新状态（只有检查点算进展）；阶段提交了一份与旧检查点相等的拷贝。一个阶段可以反复运行自己，只要检查点在变：示例 13 的计时器只有一个 tick 阶段，每次提交“tick，n 加一”，阶段名不变，检查点在变，规则 5 继续。

memo 用来记住一个小决定。runtime.memo(name, candidate) 只在该名字仍为空时提交候选值，无论如何都返回存储的胜者；两次并发写入 a 与 b，都会得到 a。memo 熬过重启，在任务结束时丢弃，提交 memo 不算进展。示例 13 用 memo 保证每个 tick 只打印一次：第一个进程打印 tick 2 后、提交 n=3 之前关闭，第二个进程重跑 tick 2 时发现 memo 已存在，跳过打印。另一个要点是：runtime.sleep(until) 不持久。关闭 Harness 会取消它，下一个进程从检查点重启阶段。需要跨重启的截止时间，必须写进检查点。

最后是调度器。它在任务被提交、扩展被安装或 resume() 被调用时寻找可以启动的任务，按种类查找代码，在一次提交中把任务设为 running 并创建调用。它有一个极其重要的性质：从不因为代码缺失而终结一个任务。

找不到代码时，任务被阻塞，原因有三：missing_task（没有注册这个名字），task_too_old（存储的版本比代码新），migration_failed（代码更新，但 migrate 缺失或抛错）。被阻塞的任务没有失败，记录不变，仍算未完成的工作，注册表一变化就重试。阻塞是派生的运行时状态，不被持久化。只有带中止标记且没有代码可以接手的任务，才以 orphaned 结束。这个性质让升级与回滚变得安全：部署了一个漏掉某扩展的版本，相关任务只是暂停，补上扩展就继续。

第 16 章副作用夹在两次提交之间

Harness 可以原子地提交自己的记录，却无法让一次扣款、一次部署或一封邮件与这些记录原子地发生。如果进程恰好在扣款之后死去，客户付了钱没有？副作用是任何改变存储之外世界的东西：一笔付款、一次 API 调用、另一台机器上的一个文件。副作用不能在提交内运行（不变量 4），因为提交持有 Session 的写入队列，在那里等待网络会阻塞所有其他写入者。所以副作用总是发生在两次提交之间，而进程可能在两者之间死去。规范的回答是一个固定的形状：提交意图阶段，执行外部副作用，提交结局或下一阶段。

规范自己的支付示例分三部分。prepare 生成一个幂等键，作为下一个检查点提交。charge 用这个键执行副作用，然后在同一次提交中追加回执条目并结束任务。中止处理器撤销扣款并提交 aborted。新进程打开存储时，每个运行中的任务回到 pending，带着它的检查点；检查点而不是进程说明任务停在哪里。在意图提交之前崩溃，重开发现检查点 prepare，重跑 prepare，没有任何扣款被发出。在意图之后、扣款之前崩溃，重开发现检查点 charge，执行扣款，这是第一次。在扣款之后、结局之前崩溃，重开同样发现检查点 charge，再次执行扣款，用同一个键。在结局提交之后崩溃，重开发现 terminal，什么也不运行。

中间两种情况在新进程看来完全相同。规范的原话是：在意图阶段重开，意味着副作用可能已经发生。Harness 无法知道请求在进程死亡前是否已到达支付服务，所以你的阶段必须两种情况都正确。规范给出三种做法：安全重试，轮询外部句柄，或记录中断。安全重试是发送一个在意图阶段创建、存于检查点的幂等键；恢复测试里，转账服务在关闭与重开之间被调用两次，却只执行一次，因为两次都带着同一个键。轮询句柄适用于远端返回操作 ID 的系统：等待之前先提交它，然后向远端询问结果，生成任务对延迟的模型调用就是这样做的。记录中断适用于两者都不可行时：提交一个说明“副作用可能发生也可能没有发生”的结局，未标记 safe 的工具调用正是如此。

有三条从这个形状直接推出的实践。键要在意图阶段创建：在副作用阶段内创建的键每次重跑都会变，去重就失效了；示例 12 从任务 ID 派生键，购物捕获在任何扣款之前已在第 4 次提交写入“charge-a”。结局与它的后果一起提交：终态提交原子地写入结局、追加结果条目、退役任务的文档、结算它回答的提交；分成两次会留下“回执存在但任务仍存活”的窗口。同一阶段内的第二个副作用用 memo 守护：购物订单的 charge 阶段只在 memo chargeId 为空时调用服务；在调用与 memo 之间崩溃仍会重复调用，所以调用本身必须能容忍这一点。

内置任务遵循同一个形状，所以它们的恢复是可预测的。工具任务在运行工具之前提交意图“execute、参数、重放策略”，重放策略来自工具，默认 unsafe。正常运行中，同一个阶段接着运行工具并提交结果，所以 execute 阶段只有恢复时才会被单独到达。在那里，只有存储的策略与当前的策略都是 safe 时，它才重跑工具；否则它把调用提交为失败，附上中断说明。

这条规则比看上去更严格。两份策略都要同意：工具改为 unsafe 后不重跑，存储为 unsafe 而工具后来改为 safe 也不重跑。工具缺失视为 unsafe。重跑会按会话当前的工作目录重建执行环境，可能与第一次不同。在意图提交之前崩溃则便宜得多：任务仍在 call 阶段，整个调用从头运行一次，beforeTool 也重跑。手册对内置工具的结论很简单：read、write、edit、bash 都没有声明 replay，所以崩溃在调用中途时它们总是被中断。手册还列出了框架写入的几种错误结果：工具不可用、参数无效、被钩子阻断、执行抛错、中断与中止，前三种任务以 completed 结束，后三种保留已报告的输出。

生成任务用轮询而不是重试来处理延迟的提供方。提供方返回一个延迟句柄时，任务提交一个带句柄与轮询时间的检查点；循环中任何一处崩溃，重开时检查点仍指向远端操作，中止处理器可以用存储的句柄取消它。普通失败则走重试：默认三次，基础延迟 2,000 毫秒，每次翻倍，上限 60,000 毫秒；上下文过长时先压缩一次再重试；延迟句柄的默认轮询间隔是 5,000 毫秒。

对照实验：同一笔扣款的三种写法

副作用三明治的价值，在把错误写法与正确写法并排放时最为清楚。设想同一个支付任务，有三种实现。

第一种写法把幂等键放在副作用阶段内生成：charge 阶段开头生成一个新键，调用支付服务，然后提交结局。正常运行时它与正确写法毫无区别。但如果进程在调用之后、结局提交之前死去，重开时 charge 阶段从头再跑，生成的是另一个新键，支付服务看到的是两笔不同的请求。手册对此的提醒很直接：在副作用阶段内创建的键每次重跑都会变，去重就失效了。这种错误在所有测试里都看不出来，只在崩溃恰好落在那个窗口时才显现。

第二种写法把键放对了位置，却把结局拆成两次提交：先提交 terminal，再追加回执条目。正常运行同样没有问题。可一旦在两次提交之间崩溃，存储里就有一个已结束的任务和一笔找不到回执的付款；或者反过来，若先追加回执再结束任务，就有一张回执和一个仍然存活、重开后会再次扣款的任务。终态提交之所以要原子地写入结局、追加结果条目、退役任务文档并结算它所回答的提交，正是为了消除这个窗口。

第三种写法是规范的写法：prepare 阶段生成键并作为检查点提交；charge 阶段读取检查点里的键，调用服务，然后在同一次提交里追加回执并结束任务；中止处理器用同一个检查点撤销扣款。对它做任何位置的崩溃实验，结果都可预测：要么什么也没发出，要么带同一个键再发一次，要么什么也不做。三种写法的代码量几乎相同，差别只在于“哪个值在哪次提交里”。这正是 Pi Durable 把持久性交给开发者的方式：它不替你决定，但让正确的决定可以被写下来。

这一章的结论可以用一个框写下来：Pi Durable 从不撤销外部副作用。失败的提交只回滚框架自己的记录。撤销一笔扣款是远端系统的事：它的幂等键、它的取消接口、它的操作句柄。这也是“恰好一次”这个说法需要谨慎的原因。发布文章说 requestId 让一次提交恰好一次，Hacker News 上有人对此提出异议。两种说法都对，只是指的不是同一件事：requestId 保证的是提交被接受恰好一次，而不是工具的副作用恰好一次。

恰好一次的准确含义
  • 提交的接受：同一会话内同一 requestId 只产生一条提交记录。
  • 工具的副作用：unsafe 工具在中断后不重跑，safe 工具可能运行两次；远端去重靠你的幂等键。
  • 模型请求：中断的请求可能被付费两次。

第 17 章收件箱决定一条消息何时落地

智能体还在回答第一个问题，用户又打了第二条消息。它应该打断、等待，还是被拒绝？如果一秒钟后进程死了，这条消息会不会丢？Pi Durable 用一条规则回答：消息在发生任何其他事情之前先被提交。

提交（submission）是你交给一个会话的东西的持久记录，分两种。输入是用户消息，它可能启动一次运行，即回答它的模型调用与工具调用。写入是不询问模型就向转写追加一个条目，例如来自你的应用的一条备注。Conversation.submit() 用一次提交写下这条记录，返回一个带 status()、wait() 与 abort() 的句柄。

一条提交处于四种状态之一。queued 表示在等待；placed 表示输入的消息已进入转写、有一次运行在回答它；done 表示它有了条目，对输入而言还有了回答；unanswered 表示它在没有回答的情况下结束，附带原因：被撤回、陈旧、被重置、模型错误、没有模型、故障，或者它的任务成为孤儿的原因。wait() 只在 done 或 unanswered 时返回。走哪条路径取决于一个问题：会话忙吗？空闲且收件箱为空时，输入立即 placed 并启动运行，写入立即追加并完成。忙，或已有其他项在排队时，提交进入收件箱排队。忙且 whenBusy 为 reject 时，什么也不写，submit() 抛出 ConversationBusy。requestId 已用过时，什么也不写，返回已有的提交。最后这一条让重试变得安全：提交超时或进程重启后，用同一个 ID 再发一次，得到的是同一条提交而不是第二份拷贝。ID 的作用域是一个会话。

排队的提交等在 pi.inbox 里，这是每个会话一个的小型内置文档，分叉从空收件箱开始。每一项带一个模式，说明它何时可以落地。steer 的含义是“当前工具调用一结束就告诉智能体”，消息加入正在进行的运行。followUp 的含义是“当前回答之后再处理”，消息启动下一次运行，这是 whenBusy 的默认值。write 是排队的写入，在下一个机会落地，排在任何用户消息之前。

边界是排队项进入转写的那次提交，共有两种。postTools 边界在运行进行中、一轮工具调用之后执行，取走所有写入与第一条 steer。final 边界在运行成功结束时执行，取走所有写入、第一条 steer 与第一条 followUp。把 steeringMode 或 followUpMode 设为 "all"，可以一次取走该模式的全部项，默认一次一项。边界先放写入，再放用户消息，各自按提交顺序。所以排在重置或压缩摘要之前提交的消息，会落在它之后，模型在新的上下文中读到它。

只有成功的运行才执行 final 边界。失败或被中止的运行把自己的输入结算为 unanswered，收件箱原样不动。这带来一个容易被忽略的后果：失败运行之后，排队的 followUp 仍留在收件箱里，它们的 wait() 不会返回，直到有新的提交进来或你撤回它们；下一次提交会排在它们后面，所以较早的 followUp 先运行。Submission.abort() 撤回仍在排队的提交，它以 aborted 结算为 unanswered；一旦 placed 就来不及了，调用返回“已 placed”或“已结算”。Conversation.abort() 撤回所有排队的输入但保留排队的写入。

崩溃对这些都没有影响：每条记录与每个收件箱项都已提交。重开之后，排队的 followUp 仍会在被中断的运行结束后运行。丢失的只有内存中的等待者，用 harness.submission(id) 取回新句柄再等待即可。与第 3 章对照，编码智能体里 steer 与 follow-up 的语义几乎相同，差别只在一处：那里的队列在内存里，这里的队列是一个被提交的文档。

会话是否忙、屏幕此刻该显示什么，这两个问题的答案都在另一个内置文档 pi.live 里。

pi.live 的每个字段都是可选的，空闲会话的值是空对象。run 是锁：它存在时会话就是忙的，submit() 不检查别的。run 记录这次运行要回答的提交与负责回答它们的生成任务。一次运行是一串生成，每轮一个；轮与轮之间，锁被交接而非释放：旧的生成创建下一个，并在同一次提交中改写 taskId；恰在此刻落地的 steer 被追加到 inputs。运行结束时，一次提交结算所有列出的输入，删除 run、generation 与 tools。generation 描述进行中的模型调用：尝试次数、到目前为止的回答、等待重试的时间与错误、延迟提供方的轮询时间。tools 列出这一轮的工具调用：名字、状态、到目前为止的输出与完成后的结果条目。

pi.live 与其他东西一样被提交，所以晚连接的界面与重启后的进程看到同一幅图。崩溃丢失的只是最后一次成功进度提交之后的内容，这个间隔可以超过配置的节流时间，因为存储延迟与输出节奏都会拉长它。节流时间本身在 1.0.3 起可配置 [manual vs code]：手册把进度节流描述为固定的 100 毫秒，代码自 1.0.3 起暴露 partialIntervalMs 与 outputIntervalMs 两个设置，默认值仍是 100 毫秒；1.0.4 进一步规定，字段为 undefined 时保留默认值。

多个客户端观察同一段对话时，视图层还有两条值得知道的规则。一个落后超过一百帧的消费者会被折叠为最新值，所以消费者不能依赖看到每一次更新。晚加入者从当前快照开始，没有重放也没有游标；Cloudflare 文档说得更直接：没有可以从中恢复流的游标。这就是“多人引导同一智能体”的准确含义：多个客户端连接到一个拥有存储的宿主进程，由它扇出视图；写入全部经过这一个 Harness，没有多写者合并，也没有用户身份。

第 18 章文档、分叉与压缩共用一套历史

应用自己的状态放在哪里，决定了它能否与转写保持一致。Pi Durable 的答案是文档：用 defineDoc 定义的类型化 JSON，存放在转写旁边，由 Chord 跟踪，与条目在同一次原子提交中变化。

文档定义有几个字段。scope 决定所有者与寿命：session 文档被所有会话共享，直到你退役它；conversation 文档属于一个会话；task 文档属于一个任务，任务结束时自动退役。history 决定旧值是否可读：latest 只保留当前值，rewindable 保留每一次存储的变更，于是可以查询“任意条目写入时它的值”。fork 决定分叉的会话从什么开始：current 拷贝父会话的当前值，asOf 拷贝分叉点那一刻的值（只有 rewindable 文档还保留着它），initial 什么也不拷贝，分叉第一次访问时调用 initial() 创建一份新的。只有会话作用域的文档选择 history 与 fork，所以合法组合恰好七种。

内置文档分布在两个组合上：pi.live、pi.inbox、pi.usage、pi.provider 是 latest 族，pi.agent 是 rewindable 加 asOf。后者的意义在于：从某个较早的条目分叉出去的会话，继承的是那一刻的模型、工具与指令配置，而不是父会话后来改成的样子。文档家族是同一定义下由字符串键区分的多份文档，例如“每个文件一份审阅文档”。

文档的存储方式是基底加 Chord 操作增量。没有 checkpointWhen 时，增量会无限增长；rewindable 的历史永不释放空间；存储中的版本比代码新时，旧代码会被阻止读取。这三条都是规范 §12 所说的“契约，而非邀请你添加防御机制”：框架不会替你判断何时该存一份完整基底，因为“自动检查点启发式”被明确列为非目标。

会话与分叉的形状和编码智能体不同。会话是按时间排列的不可变条目列表。分叉以另一个会话中的某个条目为父，继承到那一点为止的历史，但不拷贝它。维护者在 Hacker News 上的说法是：树还在，只是更扁了。重置与交接移动一个只能前进的头部标记，不删除任何东西；Cloudflare 文档确认，Pi Durable 目前还不能删除会话。两种会话格式之间的迁移路径没有文档，实验性的 durable 编码智能体也省略了树导航。

压缩在 Durable 中是一个任务，pi.compaction。它选择上下文的一个前缀，请模型总结，追加一个摘要条目；条目的 head 指向第一个原样保留的条目，于是模型的上下文从摘要开始，接着从那里继续。有四种启动方式：手动调用 compact()、生成任务在后台预算处触发、生成任务在阻塞预算处触发、上下文过长时触发。前两种不让运行等待，摘要作为写入提交，在下一个边界落地；后两种让运行等待，摘要直接追加，因为等待它的正是自己的生成。这是一条安全规则：正在运行的生成，不能让转写在它脚下变化。

默认预算是 reserveTokens 16,384、keepRecentTokens 20,000、backgroundTokens 32,768。压缩从不切在工具结果处。摘要请求把工具结果截断到 2,000 字符。两个摘要竞争时，陈旧头部规则决定胜负：切得最远者胜，另一个成为陈旧写入。每一次摘要尝试都要付费，落败的也一样；压缩期间的编辑可能丢失，这是规范列出的陷阱之一。用量方面，pi.usage 按会话统计，harness.usage() 汇总；如果同时把子会话的用量向上累加，子智能体的成本可能被重复计算。

两种记录模型：一行记录“发生过”，一次提交记录“可以被看见”

熟悉编码智能体的读者，最容易通过对照来理解 Pi Durable 的记录模型。两者共享转写的基本观念：只追加的条目、按位置表达的系统提示增量、保留原始条目的摘要。它们的区别在于一次写入意味着什么。

第 19 章名字在存储里，代码在内存里

智能体需要工具、系统提示与若干护栏。你还希望修复其中一个而不停止智能体，并在崩溃后重启而不丢失任何东西。Pi Durable 同时做到这两点的办法是：所有代码留在内存里，只存储名字。

扩展是一个具名的代码包，是一个带名字与至多五个列表的普通对象：tools（模型可调用的工具）、sections（系统提示的片段）、hooks（内置任务调用的处理器）、wraps（另一个扩展的工具或片段的装饰器）、tasks（你自己的持久任务定义）。每个列表都通过字符串名字与系统其余部分匹配，从不通过对象身份。注册表是扩展与 Harness 相遇的地方。createRegistry() 返回一个由你的应用拥有的对象，已含三个内置任务定义。

注册表不写入磁盘。规范的说法是：它是进程本地的，可以比 Harness 活得久，不被持久化。会话在它的 pi.agent 文档中以名字列表记录它想要的扩展；每当 Harness 需要代码，就到注册表里查这些名字。单轮捕获的数据库里，根会话的智能体文档只存了模型选择，没有任何工具或提示代码。新进程安装扩展、打开同一存储，每个存储的名字就绑定到当前承载它的代码。没有安装的名字被跳过而不是报错，再次安装后重新生效。任务定义同样如此：存储的任务以名字记录种类，没有扩展定义这个名字时，任务被阻塞而不是失败。

注册表有两种操作。install(extension) 在末尾添加新名字，或在原位置替换同名扩展；uninstall(extension) 移除持有该名字的扩展。每次变化立即生效，扩展是重载的单位。安装顺序有意义：默认情况下，每个会话按安装顺序使用所有已安装扩展。热重载就是以同一名字再次安装；运行中的调用会继续使用旧代码，资源应在运行中的调用结束后再释放。

这套设计带来一个对安全至关重要的推论：没有全局钩子。权限扩展只对选择了它的会话生效；一个显式列出扩展却漏掉权限扩展的会话，就在没有守卫的情况下运行。规范 §12 的陷阱表里，“在每个列表中都包含守卫”是单独一行；从拷贝的列表做增删时，会从宿主默认值而不是从父会话的列表开始；子会话的列表只在创建时拷贝一次，父会话后来的改变不会传到任务拥有的子会话。

钩子共七个，挂在三个内置任务上：生成任务的 beforeRequest、afterResponse、onYield、afterTools，工具任务的 beforeTool、afterTool，压缩任务的 beforeCompact。钩子在线外按扩展顺序运行；在消费它的提交之前崩溃，钩子可能重跑。必须只决定一次的钩子，用 memo(name, candidate) 记下它的决定，这是一次带门控的提交；钩子与发起它的任务共享同一组 memo，所以 memo 名要加前缀。审批就建在 beforeTool 上：它可以阻断调用或改写参数。Cloudflare 文档写道，Pi Durable 尚无工具调用的审批或权限步骤；手册与发布文章展示了用 beforeTool 加 memo 构建审批的模式。两者并不矛盾：没有内置的审批，你可以自己建一个。

每个会话自带一个智能体配置，即 pi.agent 文档：模型、思考级别、扩展、工具、指令与工作目录，通过 configure() 设置。设置从不存储，而是通过实时 getter 读取。改变默认值或安装会增加系统条目并错过提示缓存；一个嵌入当前时间的提示片段会让每次请求都不同，使缓存失效。

子智能体是一种模式而不是 API：被拥有的子会话。前台子智能体由调用它的工具任务拥有；后台子智能体使用一个锚定任务加一个报告任务。所有权构成一棵树，中止沿树向下级联，中止处理器自下而上运行。

这棵树把结构化并发带进了持久世界。中止一个会话，它的生成、生成拥有的工具调用、工具拥有的子会话、子会话的生成，全部收到中止标记；清理从最深处开始，每一层的中止处理器都必须提交一个结局。以 failed 或 aborted 结束的工具任务会连带中止它拥有的会话。框架不会强行终止不合作的扩展代码，这也是非目标之一：一个忽略中止信号的工具无法在进程内被停止，close() 会等待它。所以每一个 await 都应传入调用的上下文。

第 20 章存储后端，以及在 Cloudflare 上运行

存储契约很窄：保存记录与文档，原子地提交一批写入。包内附带三种实现，它们在持久性与速度上的取舍各不相同。

内存存储是参考实现，进程退出即丢失，适合测试与演示。SQLite 存储使用 node:sqlite，以 WAL 模式加 synchronous=NORMAL 运行，README 的原话是“最新的提交可能在断电或宿主故障时丢失”；它的可移植核心通过一个 SqliteDatabase 外观运行在 Bun 或 Cloudflare Durable Objects 上，这是推荐的后端。JSONL 存储默认不 fsync，打开时截掉撕裂的尾部，JsonlCorruptionError 永不自动修复。手册在 M3 Max 上的基准给出一个定性排序：内存查找 0.44 微秒、提交 5.5 微秒；SQLite 提交约 120 微秒、重开一千条约 1.33 毫秒；JSONL 提交约 792 微秒、重开约 249 毫秒。这些数字只用于比较，不是性能承诺。

“持久”在这里有一个精确的含义：进程崩溃可恢复，而非断电一定不丢。发布文章说框架能“熬过灾难性故障”，README 关于 SQLite 设置的说明则更保守。两者调和的方式是：杀死进程、内存溢出、部署替换，这些都不会丢失已提交的数据；断电或宿主崩溃，最新的若干提交可能丢失。需要更强保证的团队可以调整设置，或者接受这个风险。Cloudflare Durable Objects 的 SQLite 在断电语义上是否更强，目前没有核实。

单写者规则是存储层最重要的一条约束。一个存储同一时间只能被一个进程拥有，没有跨进程锁。没有任何东西阻止第二个进程打开同一个文件，两者都会以为自己是唯一的写入者；两个进程在一个 SQLite 文件上可能发出重复 ID，导致记录损坏或被悄悄替换。SQLite 的 busyTimeoutMs（默认 5,000 毫秒）只让 SQLite 等待文件锁，并不使两个 Harness 在一个文件上变得安全。实验性的 durable 编码智能体为此加了自己的锁文件。自定义后端必须通过 23 项存储一致性测试。

执行环境是另一条边界。ExecutionEnv 是文件系统加 Shell，包内附带 NodeExecutionEnv；pi-env 包提供通过 SSH 的远程执行环境。环境每次使用时从已提交状态重建，所以重跑可能得到不同的工作目录。可以给每个会话一个独立沙箱（示例 29）。自定义环境必须通过环境一致性测试。这里有一处版本差异 [manual vs code]：手册描述的是 1.0.3 的文件系统与 watch 契约及其一致性测试规模；1.0.4 把 watch 的权限错误改为报告 permission_denied，一致性测试新增三个 watch 用例，通过 1.0.3 测试的自定义环境可能在 1.0.4 失败。1.0.4 还新增了 createPowerShellTool()，手册中没有。

在 Cloudflare 上，Pi Durable 由 Agents SDK 中的 PiHarness 托管。PiHarness 是 Cloudflare 提供的“生命周期能力”，处于 beta，2026 年 10 月 2 日公告。

PiHarness 在 Durable Object 的 SQLite 上提供存储，表名以 pi_ 为前缀；有待完成工作时启动一个生命周期作业，心跳每 30 秒触发一次。驱逐、崩溃或部署（有 30 秒宽限期）之后，告警重启对象，Pi 重新打开存储。告警调用最长 15 分钟，每 10 分钟交接一次；单次超过 15 分钟的模型流可能被截断。根会话 id 固定为 "1"，不能自选会话 id；Cloudflare 建议每个用户或每个聊天一个 Durable Object。它的 API 包括 prompt、带幂等 operationId 的 submit、wait、pending、steer、abort、reset、setModel、messages、events、busy，以及 sessions.create/fork/list；harness.pi() 返回原始的 Harness。安装命令是 npm i agents @earendil-works/pi-durable @earendil-works/pi-ai，两个 Pi 包是 agents 的可选 peer 依赖，需要 nodejs_compat 标志。

Cloudflare 天然解决了两个宿主问题：单写者（一个对象一个存储）与唤醒（告警）。它也带来自己的限制：beta 叠加 experimental，15 分钟单流上限，最长约 30 秒的探测延迟，没有优雅排空，没有流游标，不能删除会话，没有审批。还有一个责任划分的问题：发布文章说可移植核心“借助一个适配器”运行在 Durable Object 中，而这个适配器由 Cloudflare 维护，不属于 Pi Durable。适配器出了问题该找谁，需要在采纳前想清楚。“无限长的对话”与 15 分钟上限并不矛盾：对话可以跨越任意多次告警，受限的是单条流。

第四篇

案例

同一套原语，落在四种不同的使用者手里：一位终端开发者、一家公司的机器人、一个人的私人智能体，以及一个先嵌入后分叉的产品。

第 21 章终端里的开发者：最低风险的起点

对大多数公司来说，接触 Pi 的第一步不是 Durable，而是把编码智能体当作日常工具交给工程师。这是风险最低、今天就能做的路径。它的价值在于模型无关：十五家以上的提供方、会话中途切换模型、订阅制的 OAuth 登录、虚拟模型路由。Hacker News 上一位用户的评价很有代表性：Pi 更可改造，而且默认不绑定任何厂商。另一项价值是让工具适应工作流，而不是反过来：行为来自扩展、技能、包、AGENTS.md 与 SYSTEM.md。

一套标准装配大致如上。安装用托管安装器或 Nix，因为它们锁定传递依赖；npm 全局安装自 1.0.1 起不再锁定。版本锁定在 1.0.4，升级前读 CHANGELOG，因为补丁版本里出现过破坏性变更。~/.pi/agent/settings.json 由平台团队统一：遥测策略、包白名单与 MCP 服务。智能体运行在 devcontainer、Docker Sandboxes 或 Gondolin 里，只挂载需要的目录，凭证经代理而不是环境变量进入。公司的技能、提示模板与守卫扩展打成一个内部 Pi 包，从 permission-gate、protected-paths 与 confirm-destructive 示例起步。如有需要，模型请求经过一个网关，自建或 Radius 均可。

这条路径上要盯住四件事。默认没有权限提示；项目信任不是沙箱；补丁版本可能有破坏性变更，例如编码智能体 1.0.3 把 Azure 提供方从 azure-openai-responses 改名为 azure，列在 Breaking Changes 下；会话文件可能含有密钥，分享前必须审查。遥测也是一项治理决定：enableInstallTelemetry 默认开启，内容是匿名的安装与更新报告以及部分提供方归属头；enableAnalytics 默认关闭；PI_TELEMETRY=0 关闭遥测，PI_OFFLINE=1 或 --offline 禁止自动网络活动。安装遥测的具体载荷，在本书查阅的文件里没有完整文档，企业推广前需要自行核实。

在这条路径上，开发者每天得到的是第一篇描述的那个循环；公司得到的是一个可以被统一配置、统一分发、统一隔离的工具。崩溃时，人就在终端前，人就是持久层。这正是编码智能体的设计范围，也是它在这里表现良好的原因。

第 22 章公司机器人：当没有人盯着终端

一旦智能体离开终端、进入 Slack 频道或值班系统，第二篇描述的缺口就全部暴露出来。Earendil 自己预告了 Slack 与 GitHub 分诊机器人；社区里有人把在 Kubernetes 上基于 DBOS 的会话存活方案换成了 Pi Durable。这些都说明目标场景的轮廓：机器人需要熬过重启，需要接受多人引导，需要在无人值守时对外部系统做出可信的动作。

一种参考形状如上。它不是 Earendil 发布的架构，而是把手册与 README 的约束组合起来的结果。Slack 事件进入一个宿主服务，宿主负责身份与授权，因为 Pi Durable 的 API 里没有任何东西识别用户。宿主把每个线程映射为一个会话，调用 submit，以 Slack 的事件 id 作为 requestId：Slack 重投同一事件时，同一 requestId 不会写入第二条提交。Harness 运行在一个进程里，拥有一个 SQLite 文件；进程由监督者管理，systemd、Kubernetes 或一把锁都可以，关键是保证同一时间只有一个进程打开这个存储。

守卫扩展被强制加入每个会话的扩展列表。这一点需要用代码而不是约定来保证，因为没有全局钩子：任何一个漏掉它的会话都会在没有审批的情况下运行。审批建在 beforeTool 上，决定用 memo 记下，使崩溃后的重跑做出同样的决定。对外部系统的写入，例如关闭工单、发布公告、修改配置，建模为任务：意图阶段生成幂等键并提交，副作用阶段带键调用，结局阶段提交回执。维护者在 Hacker News 上承认，这里缺少的是“语法糖”：一个在每次提交内部运行、让发件箱写入原子化的钩子。在它出现之前，同步到外部数据库只能通过任务来做。

把这个形状放进切换图的三种情况里看。正常路径上，每条消息先成为提交，再由运行回答，多人可以对同一线程 steer。进程被驱逐时，监督者在另一处重开同一存储，运行中的任务回到 pending，resume 之后继续；unsafe 工具写下中断结果，模型据此决定下一步。事件重投时，requestId 让重复成为无操作。三种情况都不需要人介入，这正是从终端走向服务所需要的。

剩下的是公司必须自建的部分：监督与单写者、身份与授权、强制的审批扩展、幂等键与补偿、备份、精确的版本锁定与一致性测试、成本监控。第六篇把它们整理成一份清单。

动机：拥有你自己的个人智能体

OpenAI 的 Dots 代表了一类产品方向：一个主动的个人智能体，不等你开口才工作，会记住你，会按计划做事，会在需要时停下来请你批准，并且有一台属于自己的电脑。Elvis 的问题很直接：这样的东西，能否用开源工具在很短时间内搭出来，并且完全由自己拥有？“拥有”在这里有具体的含义：模型可以换，数据在自己的存储里，行为由自己写的代码决定，没有哪一家厂商的策略模型夹在中间。

这句话值得认真对待。前面几项能力本身并不新奇，任何智能体框架都可以宣称支持定时任务或审批。困难在于“你不看着的时候”：主动意味着无人值守，无人值守意味着没有人在进程死亡时替系统回答“刚才做到哪了”。第 11 章说过，编码智能体的持久层是坐在终端前的人；一个主动的个人智能体恰恰去掉了这个人。所以它需要的不是更多功能，而是一种让崩溃变成暂停的记账方式。

逐步检查点是最直接的对应。在 Pi Durable 里，没有“不带检查点的一步”：每次模型调用是一个 pi.generation 任务，每次工具调用是一个 pi.tool 任务，它们的每个阶段都以一次提交结束。所谓“杀进程可续”，就是第 10 章那次实验在个人智能体上的重演。

在桌面任务上，这个机制有一处值得细看。键鼠动作显然不是幂等的：重放一次 ctrl+a 或许无害，重放一次“在某处点击”或“输入一段文字”可能就会出错。若这些工具保持默认的 unsafe，崩溃在动作中途时，重开后的模型会收到一条诚实的中断结果，附带崩溃前已提交的输出；一个设计良好的电脑操作智能体自然会先截一张新图，确认桌面当前的状态，再决定下一步。演示中每次动作都附带截图，恰好说明这种“先看再动”的节奏。框架提供的不是自动恢复桌面，而是一个可靠的事实：模型永远不会被告知一件没有发生的事情已经成功。

记忆的对应取决于一个设计选择：Space 如何映射到 Durable 的结构。若每个 Space 是一个会话，“在一个 Space 学到的带到所有 Space”恰好是 session 作用域文档的语义：它被所有会话共享，直到被退役；会话作用域的文档则做不到这一点。

“熬过崩溃”来自同一次原子提交。记忆文档的更新与触发它的转写条目一起写入，所以崩溃之后，记忆既不会领先于产生它的那条消息，也不会落后于它。这一点与第 11 章列出的缺口正好对应：编码智能体里，扩展在内存中维护的状态会在崩溃时消失，或与转写脱节。还有一个实际的注意点：记忆文档会随着时间增长，若不设置 checkpointWhen，Chord 增量会无限增长；若选择 rewindable，历史永不释放空间。个人智能体运行越久，这个选择越要紧。

审批是最需要谨慎表述的一项。Pi Durable 没有内置的审批步骤，Cloudflare 的文档明确这样说；手册给出的模式是 beforeTool 钩子加 memo。“审批是持久的”可以有两种搭法。

第一种是“阻断—再请求”：模型请求一个需要批准的工具，beforeTool 查不到决定，就阻断调用并把待批项写入一个审批文档；Approvals 页显示这个文档；进程即使重启，待批项仍在，因为它是提交过的记录；用户点击批准后，宿主提交文档更新与一条输入，模型再次请求，beforeTool 读到批准，用 memo 记下这个决定，调用进入意图、执行、结果三段。第二种是“审批任务”：用一个自定义任务表示需要批准的动作，阶段 request 提交待批项，阶段 await 观察审批文档，阶段 act 带幂等键执行。两种形状都依赖同一个事实：待批状态是提交过的记录，而不是内存里一个等待用户点击的 Promise。后者在进程重启时会悄无声息地消失，前者不会。

主动与定时任务同样建立在检查点之上。Jobs 例句“每天早上给我一份 Hacker News 简报”需要一个能跨越整夜的计时器，而 Pi Durable 明确规定 runtime.sleep() 不持久：关闭 Harness 会取消它，下一个进程从检查点重启阶段。所以截止时间必须写进检查点。

一个可行的写法是：一个 job 任务的检查点为“阶段 wait，at 为明早八点”；阶段内可以 sleep 到 at，但这只是为了省事；进程夜里重启，任务回到 pending，检查点里的 at 仍在；到点时向 Home 会话提交一条输入，以“job 名加日期”作为 requestId；随后提交下一个检查点“at 为次日八点”。如果重启恰好发生在提交输入与推进检查点之间，重跑会再次提交同一 requestId 的输入，而这不会产生第二份简报。这是副作用三明治的一个小实例：对外的副作用是“向会话提交一条输入”，幂等键是 requestId。

“自己的电脑”是唯一一项并非来自 Pi Durable 本身的能力。Durable 不提供桌面，也不提供截图或键鼠工具；它提供的是可插拔的工具、每会话可独立构建的执行环境，以及把这些工具调用纳入任务与提交的机制。演示右栏写着“Docker · local”，说明桌面运行在本地的 Docker 容器里；computer_click、computer_key、computer_type 是宿主侧定义的工具。把每个 Space 映射到一台独立的桌面，与手册示例 29“每会话一个沙箱”的思路一致。这一层的安全含义也与第 9 章相同：桌面与容器才是边界，Durable 不是。

换模型的能力来自 pi-ai。OpenRouter 作为一个提供方接入，每个会话的模型选择存在 pi.agent 文档里，换模型就是一次 configure()。演示中的 qwen/qwen3.7-plus 说明 My Pi 并不依赖任何单一厂商的前沿模型。最后，输入框里的那句提示语“Anything you send now runs next”几乎是第 17 章 followUp 语义的逐字翻译：会话忙时，新消息以默认的 followUp 模式排入被提交的收件箱，在当前回答完成后启动下一次运行。

这个案例说明了什么

My Pi 的意义不在于又多了一个智能体产品，而在于它展示了一种分工。产品层的东西，例如 Today、Approvals、Jobs、Memory、Connectors、Runs 这些页面，Space 的划分，桌面与截图，都由开发者自己构建；让这些东西在无人值守时依然可信的那部分，即每一步都有记录、每一个待批状态都在存储里、每一份记忆都与产生它的消息一起提交，由 Pi Durable 提供。Elvis 说他惊讶于起步之快，原因正在于此：最难做对的那一层已经存在。

它同时也展示了边界。审批、身份、桌面隔离、记忆的增长控制、定时任务的调度，这些都要自己写。个人使用时，“一个存储一个进程”很容易满足，因为只有一个人、一台机器；一旦这样的系统要服务多人，第 22 章的全部清单就会回来。帖子里“计划开源”的承诺若兑现，社区将第一次拥有一个完整的、建立在 Pi Durable 之上的个人智能体参考实现；在那之前，本章的机制对应只能是推演。

小结
  • 帖子陈述的能力：主动、在你不看时继续工作、记住你、定时任务、等待批准、自己的电脑、每步检查点与杀进程可续、记忆跨 Space、OpenRouter 换模型、计划开源。
  • Pi Durable 直接提供：任务与提交、崩溃恢复、持久文档、被提交的收件箱、可插拔工具与执行环境。
  • 需要自己构建：审批流程、桌面与键鼠工具、定时调度、界面、身份与多用户。

第 24 章OpenClaw：先嵌入，后分叉

OpenClaw 是 Pi 官网至今仍列为 SDK 集成范例的产品。它的历史提供了另一种视角：用 SDK 嵌入一个开源智能体循环，能走多远，最终会走向哪里。

OpenClaw 早期通过 createAgentSession 把 Pi 嵌入自己的产品，依赖固定在 0.61.1。它在此基础上构建了一个规模可观的产品。随后它迁移到自己的运行时 @openclaw/agent-core；OpenClaw 的文档写道，外部智能体框架包已经全部移除，pi 只是一个遗留别名，仅 pi-tui 仍是依赖。Pi 官网把 OpenClaw 列为集成范例的说法因此已经过时。

这段历史同时证明了两件事。第一，嵌入是可行的：一个小而清晰的循环足以支撑一个真实的产品。第二，分叉是一个可能的终点：当产品的需求与上游的方向分开，或者上游的变更节奏成为负担时，MIT 许可让团队可以把代码拿走自己维护。对于考虑路径二（嵌入 SDK 或 RPC）的公司，OpenClaw 的经历是一个提醒：从第一天起就把“有一天要自己维护这段代码”算进成本。Pi 的贡献模式加重了这一点：新贡献者提交的 issue 与 PR 默认被自动关闭，每天审阅一次；一个上游修复可能需要事先建立的关系，规划时应当预留打补丁或分叉的余地。

第五篇

为何奏效，以及边界在哪里

一条小规则为什么能支撑起崩溃恢复、多人引导与长对话；以及它明确不承诺的东西。

第 25 章真正让它奏效的是什么

回顾前四篇，可以发现 Pi Durable 的种种行为都来自同一个源头：每一个可见的事实都能回溯到一个持久的原因。屏幕上的一行工具输出，对应一次进度提交；一次提交，对应一个处于某个阶段的任务；任务的检查点说明它在哪一步；如果那一步是副作用，检查点里还有一条事先选定的重放策略。下一个进程因此不必猜。它读到的检查点要么说“尚未开始”，要么说“可能已经发生”，然后按策略行事。

这个链条之所以可靠，依赖四个设计决定，每一个都有明确的代价。

第一个决定是没有易失路径。所有进度都必须提交才能显示，这意味着流式输出的流畅度受限于进度提交的节奏，默认每 100 毫秒一次，每次都是一次存储写入。换来的是：观察者看到的与存储里的永远一致，晚加入的客户端、重启后的进程与原来的屏幕看到同一幅图。规范把“可见但不持久的发布”列为非目标，并非遗漏，而是代价被有意识地接受了。

第二个决定是副作用不上线。所有会话共享一条变更线，任何在提交内部等待网络的代码都会阻塞全部会话。把副作用移到线外，于是每个副作用都被夹在两次提交之间，形成意图、副作用、结局三段。这个形状让每一个崩溃点都有定义好的恢复方式，代价是开发者必须把每一个外部动作拆成阶段，并为中间那个“可能已发生”的状态写出正确的代码。

第三个决定是代码与数据分离。注册表从不持久化，会话只存名字。重启因此很便宜：新进程安装扩展、打开存储，名字自动绑定到当前代码；热重载就是同名再安装；部署漏掉一个扩展，相关任务只是被阻塞而不是失败。代价是没有全局钩子，一个忘记列出权限扩展的会话就在没有守卫的情况下运行。

第四个决定是用契约代替防御。规范 §12 列出 38 条 API 陷阱，把它们定位为“契约，而非邀请你添加防御机制”；手册的评价是“几乎没有一条在运行时检查”。注册表只检查片段键与同一扩展内工具名的唯一性；保留名、种类冲突与不可变性都交给你的测试与评审。这让代码库保持在可以通读的规模，发布文章称大约十五万 GPT token；代价是错误不会在第一时间以异常的形式告诉你，而是在负载、并发或崩溃下才显现。手册给出三个代码评审问题，能抓住大部分此类错误：提交回调里的任何 await 会离开进程吗？有代码写入一个它并不拥有其运行的会话吗？有消费者修改它读到的值，或者依赖看到每一次更新吗？

把这四个决定放在一起看，Pi Durable 的哲学与编码智能体是同一个：给出少量正确的原语，把其余的交给使用者。编码智能体的原语是循环与只追加的树；Durable 的原语是提交、任务、文档与收件箱。两者都刻意不做“产品功能”。官网的说法是“原语，而非功能”：别的智能体内置的功能，你可以自己构建。

为什么这种做法在智能体领域格外合适？因为智能体的行为变化得太快。今天的计划模式、子智能体、审批流程，半年后可能完全换了形态；把它们固化进框架，框架就会被它们拖着走。而“只有已提交的状态可被观察”这样的规则，与智能体做什么无关，只与“进程会死”这一永恒事实有关。规则越与具体功能无关，就越不容易过时。

与通用持久执行引擎相比，这种做法的位置也很清楚。Temporal 一类引擎提供确定性重放、活动重试与一个独立运维的集群；LangGraph 的检查点在恢复时让节点从头重跑；Temporal 自己的说法是“检查点不等于持久执行”，总得有东西检测失败并重启。Pi Durable 是一个嵌入式库，没有集群；它的任务有显式的阶段与检查点，调度器在 open() 时恢复工作，但监督进程仍然是宿主的事，这一点与 LangGraph 的局限相似。它的保证比通用引擎弱（单进程、无跨进程锁），基础设施也少得多。对一个只想让自己的智能体熬过重启的团队，这往往是一个合适的取舍。

第 26 章它不保证什么

一个框架的边界和它的能力一样需要被清楚地陈述。Pi Durable 保证一个进程、一个存储之内发生的事；监督、身份、备份与远端的恰好一次，都由宿主自己构建。

逐条看。工作从最后一个检查点恢复，但只有在有人重新打开存储时才会发生；部署、内存溢出与崩溃，都要由你的监督者发现并处理。每个存储一条变更线，但没有跨进程锁；确保恰好一个进程拥有一个存储，是宿主的工作。副作用之前先提交意图，但远端的恰好一次要靠幂等键与可轮询的句柄；没有标记 safe 的工具根本不会重跑，模型拿到的是中断结果。beforeTool 钩子可以阻断或改写调用，但只在选择了它的会话里；用户、认证与权限，API 里一样都没有。存储只打开一致的状态，JSONL 会丢弃撕裂与未确认的尾部，但没有备份，也没有自动的损坏修复。

规范最后列出十一项“最初没有”的东西，它们是范围决定而不是有待绕过的缺口。没有整个 Session 的单一可观察树，要观察会话视图、文档或任务图。没有可见但不持久的发布。没有内核级语义事件日志，智能体事件从提交派生而非存储。没有会话作用域之外的可回溯文档。没有自动检查点启发式。不会自动挂载第三方视图。没有 CRDT 或离线多写者合并。不把 Chord 操作翻译成 SQL。JSONL 没有全局压缩或修复。不兼容已移除的 Pico 原型。不强行终止不合作的扩展代码。

除此之外还有几项值得单独列出的缺失：没有子智能体 API（只有模式），没有发件箱模式（要同步外部数据库，只能通过任务），不能删除会话，没有流游标。持久性的含义需要再说一次：进程崩溃持久，而非断电一定持久。SQLite 以 synchronous=NORMAL 运行时，最新的提交可能在断电或宿主故障时丢失；JSONL 默认不 fsync；进度提交本身有节流间隔。

还有一些不确定之处，本书无法给出结论。Cloudflare Durable Objects 的 SQLite 在断电语义上是否比 Node 的设置更强，没有核实。编码智能体长期是否会迁移到 Durable 之上，迹象互相矛盾：src/experimental/services 显示客户端与服务端正在从已移除的 AgentHarness 迁到 pi-durable，发布文章却说 Durable 不取代编码智能体。规范落后于代码：§2.2 仍写着“Pico5 尚未实现”，而 Pico5 正是 Pi Durable 的内部名称 [manual vs code]。这些都提醒采纳者：以代码为准，并预期变化。

不保证清单
  • 不重启你的进程；不阻止两个进程打开同一个存储。
  • 不识别用户；不内置审批或权限。
  • 不撤销外部副作用；不保证副作用恰好一次。
  • 不保证断电后最新提交不丢。
  • 不保证 API 在任意两个版本之间稳定。

第 27 章许可、治理、遥测与发布节奏

技术机制之外，采纳一个开源项目还要回答几个非技术问题：谁拥有它，许可是否稳定，它向外发送什么，它变化得有多快。

所有已发布的包都采用 MIT 许可，LICENSE 写着“Copyright (c) 2025 Mario Zechner”；evals 包没有许可。名称与标志是 Earendil Works 的商标。Mario Zechner 在 2026 年 4 月的文章中说明了治理安排：Pi 归 Earendil 所有，商标属于 Earendil；核心“永远 MIT，不容商量”；未来会有两个层级，Fair Source（DOSP）的增值功能与专有的企业和云功能，“尚未构建”；不要求 CLA 或 DCO。项目由三个人决定（Zechner、Ronacher、Hanna），背后是一家有风险投资的公司。Radius（radius.pi.dev，早期 alpha）是 Earendil 的商业 AI 网关，提供组织级控制与分析，已经接入 /login、/share 与 /bug。哪些未来功能会落入 Fair Source 或专有层，目前没有说明。

对公司而言，这组事实的含义是：MIT 允许分叉，核心的许可承诺明确；但商业层级会出现，网关已经与命令行集成，长期的功能边界需要持续观察。遥测是第 21 章已经提到的治理项：安装遥测默认开启，分析默认关闭，环境变量可以关闭或离线运行，安装遥测的确切载荷需要自行核实。

发布节奏是另一个需要正视的事实。

1.0.0 到 1.0.4 在五天内发布（10 月 1 日至 5 日），编码智能体自 5 月以来已有 57 个版本。补丁版本中出现过破坏性变更：Durable 1.0.3 要求自定义文件系统与 Shell 实现 openBinaryReader、openDirReader 与 watch，并改为以参数数组执行命令；1.0.4 改变了 watch 的错误语义并新增环境一致性检查。这些对一个实验性包来说是意料之中的。值得注意的是编码智能体 1.0.3 也把 Azure 提供方改名列为破坏性变更，这削弱了“稳定 1.0”的信息。本书没有找到书面的 SemVer 或 LTS 政策。

结论很直接：精确锁定版本，阅读每一个 CHANGELOG，在 CI 中运行存储与环境的一致性测试。高频发布对修复有利，对升级有成本。npm 上的下载数字（编码智能体每周约 520 万次）主要来自 CI 与传递安装，不是用户数；发布文章所说“每周数十万人”没有可核实的来源。Hacker News 上的发布帖获得 508 分、74 条评论，说明关注度很高，但关注度不等于生产成熟度。

公司采纳指南

四条路径，一份清单。先选对路径，再补齐框架刻意留给你的那些工作。

第 28 章四条路径，按风险排序

把前面的机制与案例收拢起来，公司采纳 Pi 有四条路径，风险依次升高。

路径一，把编码智能体当作日常工具。适用于想要模型无关命令行的个人工程师与平台团队，风险最低，今天就能做。要做的事是第 21 章那套标准装配：托管安装器或 Nix，统一的设置，容器内运行，内部 Pi 包，可选的网关。要盯住的是：默认没有权限提示，项目信任不是沙箱，补丁版本的破坏性变更，会话文件里的密钥。

路径二，在内部工具里嵌入智能体循环。适用于构建 CI 机器人、内部命令行、IDE 或聊天前端的团队。用 RPC 获得语言无关的进程隔离，或用 SDK 获得进程内控制；显式选择工具，因为 SDK 默认不启用 Codemode 与 MCP。要盯住的是：会话仍是 JSONL，没有运行中的持久性；要让它熬过 Pod 重启，需要自己补，DBOS 的例子说明了这一点。OpenClaw 的经历说明这条路走得通，也说明分叉是可能的终点。

路径三，在 Node 或 Bun 上用 SQLite 构建 Pi Durable 应用。适用于构建 Slack、值班、分诊或调查智能体的产品团队，这些智能体必须熬过重启并接受多人引导。要做的事是：SQLite 存储，一个存储一个进程，置于监督者之下；在强制扩展中实现身份、授权与审批钩子；把幂等工具标为 safe；把外部写入建模为带幂等键的任务；建立备份；锁定版本并在 CI 中运行存储与环境一致性测试。起点可以是包内示例 00 到 31，尤其是 20（收件箱）、13（恢复）、22 与 23（子智能体）、27（计划模式）、29（每会话一个沙箱），以及度假规划演示。

路径四，在 Cloudflare Durable Objects 上用 PiHarness 运行 Pi Durable。适用于已经在 Workers 上、希望每个会话一个智能体的无服务器部署的团队。做法是 Agent 加 this.lifecycle.use(new PiHarness(...))，模型用 Workers AI 或 AI Gateway，operationId 取自入站事件 id，传输自选。要盯住的是：beta 叠加 experimental，15 分钟单流上限，没有审批，没有事件游标，不能删除。优势是单写者与唤醒问题由平台解决。

决策的启发式很简单：路径一与二对大多数公司今天就是合理的，前提是做好隔离；路径三与四适合试点与内部工具，前提是团队能够吸收 API 的变动，并且自己拥有安全层。

与其他选择相比，Pi 的位置可以用几句话概括。厂商集成的智能体与托管服务内置权限策略，例如自动允许、总是询问、自动判断三档；Pi 模型无关，没有内置权限，Pi Durable 自托管或运行在 Cloudflare 上，而非托管服务。代码优先的智能体框架通常借助外部工作流引擎获得持久性；Pi Durable 把持久性做进框架自己的存储模型。图式状态机框架在恢复时让节点从头重跑；Pi Durable 的任务有显式阶段与检查点，但宿主仍然负责监督进程。通用持久执行引擎提供更强的保证，也需要运维一个集群；Pi Durable 是嵌入式库，保证更弱，基础设施更少。Cloudflare 自己的 Project Think 是另一种有主见的框架选择，PiHarness 则把循环、转写与恢复交给 Pi。

第 29 章试点之前要建好的东西

框架刻意留下的每一项空白，都会变成你的工程工作与治理面。好处是不被锁定在某一家厂商的策略模型里，代码库也小到可以通读。下面这份清单把前面各章分散的要求收拢在一起，可以直接用于试点评审。

监督与单写者是第一项。一个存储一个进程，由 systemd、Kubernetes 或 Cloudflare 的对象模型保证；监督者负责在进程死亡后重启并重新打开存储。打开本身是一次写入，监控面板不应直接打开正在使用的存储；对 SQLite，可以用一个独立的只读连接安全地读取实时数据库，手册的捕获脚本就是这样读取运行中的行的。重开之前安装好所有扩展，这样恢复的工作立刻继续，而不是停在阻塞状态。

身份与授权是第二项。API 里没有任何东西识别用户。src/experimental/services 的说明写着“身份就绪后再加认证”，说明连 Earendil 自己的实验栈也还在等待这一层。在此之前，宿主必须在 Harness 之外完成认证、授权，并决定每个用户能 steer 哪些会话。

审批与守卫是第三项。用一个强制的扩展实现 beforeTool 审批，用 memo 记下决定；用代码而不是约定保证它出现在每个会话的扩展列表里，包括子会话的列表。所有有外部副作用的工具保持默认的 unsafe，只有真正幂等的工具才标为 safe。

副作用与补偿是第四项。外部写入建模为任务，幂等键在意图阶段生成并写入检查点；无法幂等的动作，提供可轮询的句柄或在中止处理器中写好补偿逻辑。成本监控要能识别重复计费：中断的模型请求可能被付费两次，落败的压缩摘要同样计费，子智能体的用量可能被重复累加。

数据与版本是第五项。为存储建立备份与恢复演练，JSONL 没有自动修复。精确锁定所有 Pi 包的版本，阅读每一个补丁版本的 CHANGELOG，在 CI 中运行存储与环境的一致性测试，这样补丁版本里的破坏性变更会在测试里而不是生产中暴露。遥测策略写进配置。

运行环境是第六项。智能体进程或它的工具运行在容器或微虚拟机里；凭证经代理注入而非环境变量；在 Cloudflare 上确认单次模型流能在 15 分钟内结束。最后，为上游关系做好准备：新贡献者的 issue 与 PR 默认自动关闭，关键修复可能需要你自己打补丁。

这份清单看起来很长，但它的每一项都有明确的出处，也都有明确的完成标准。与其说它是 Pi 的缺点，不如说它是任何一个无人值守智能体系统本来就需要的工作，只是 Pi 把它们清楚地摆在了你面前，而不是藏在某个托管服务的条款里。

附录 C术语

术语含义
循环（loop）转写交给模型、执行工具、结果追加、再交给模型，直到不再有工具调用
轮（turn）一次助手回答及其发起的工具调用
运行（run）从被接纳的输入到最终回答的一串轮次；运行期间会话为忙
agent_settled编码智能体一次运行真正结束的事件；prompt() 在此返回
steer / followUp运行中到达的消息：前者在工具轮后并入当前运行，后者在运行结束后启动新运行
Harness一个打开的存储加上运行智能体的机制：会话句柄、提交、调度器、视图
Session 内核拥有唯一变更线与全部记录的核心；一次一个提交
提交（commit）一次原子保存，跨越条目、任务记录与文档
条目（entry）不可变的转写记录
任务（task）依附于一个会话的持久状态机，按阶段提交检查点
检查点（checkpoint）指明下一阶段并携带其所需数据的小型 JSON 值
副作用三明治提交意图、执行副作用、提交结局的固定形状
replay工具的重放策略：safe 可在崩溃后重跑，unsafe（默认）写入中断结果
提交记录（submission）交给会话的输入或写入的持久记录；状态 queued / placed / done / unanswered
边界（boundary）排队项进入转写的那次提交：postTools 或 final
文档（document）由 Chord 跟踪的类型化 JSON，作用域为 session、conversation 或 task
注册表（registry）进程本地、从不持久化的扩展集合；会话只存扩展名
memo任务记录上先写者胜的小型存储值，用于记住一次性决定
阻塞（blocked）找不到可运行代码的任务的派生状态：missing_task、task_too_old、migration_failed

把 My Pi 再读一遍，会发现它几乎是一份「哪些状态必须跨进程存活」的验收单。定时任务要在关机后仍能被唤醒；审批不能只活在某个浏览器标签页的内存里；跨 Space 的记忆如果只存在于聊天滚动条，换一个 Space 就会失忆；中途被杀掉的工具调用如果没有检查点，重启后只能靠人复述上下文。Pi Durable 并不替你实现桌面操控或模型路由，它提供的是把这些可见状态写成可提交记录、并在崩溃后按同一规则恢复的宿主骨架。OpenRouter 换模型、Docker 桌面、Jobs 面板，都是应用层选择；选择一旦做错可以改，而「未提交就不可观察」这条规则一旦违背，恢复语义就会塌陷。
