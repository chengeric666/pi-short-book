Pi，持久地：最小智能体运行框架在做什么，以及你的公司是否该用它

这是一份给技术管理者与工程师的简明读本。它从第一性原理说明 Pi 1.0 编码智能体与 Pi Durable 在做什么、为什么这样设计、以及采纳时必须自己补齐什么。

怎么读这本书

先看机制，再看为什么它管用，最后再决定是否采用。数字只来自可引用的来源；没有来源的地方，我们只做定性说明。

Pi 不是单一产品。它首先是一个 MIT 许可的 TypeScript 单体仓库（monorepo），其中包含编码智能体 CLI、统一模型 API、以及实验性的持久化运行框架 Pi Durable。公司若把「Pi」当成一个黑盒 SaaS，就会误判风险面。

Chapter 1

智能体运行框架在做什么

去掉所有产品包装之后，编码智能体几乎总是同一件事：把用户话交给模型，把模型要的工具调用执行掉，把结果贴回对话，再问模型下一步——直到它不再要工具。

一个最小循环

假设你说：「把 README.md 第一行读出来。」在 Pi 编码智能体里，大致会发生：

  1. 会话把你的话写成一条用户消息，并写入会话文件（JSONL）。
  2. 运行时组装上下文：系统提示词、项目说明文件（如 AGENTS.md）、可用工具描述、近期对话。
  3. 模型流式返回：它决定调用 read，并给出路径参数。
  4. 运行时执行工具，得到文件内容，再作为工具结果写回会话。
  5. 模型看到结果后，用自然语言回答你。若不再需要工具，这一轮结束。

Pi 把「一轮自动工作结束」标成 agent_settled。注意：这与内部某次模型尝试结束的 agent_end 不同。若你的程序要等「模型答完且没有排队工作」，应等待 agent_settled。

把这件事想成两层时钟很有帮助。内层时钟是「模型的一次尝试」：请求发出、流式 token 回来、可能触发工具、再进入下一次尝试。外层时钟是「用户的一次 prompt() / 一次交互回合」：其间可能发生多次内层尝试（例如上下文溢出后压缩再试、或 steer 插入后继续）。产品代码若只听 agent_end，会在外层尚未结算时误以为空闲。手册里的一次捕获记录了两轮、29 个会话事件、四次落盘——即便用假模型，事件形状也说明：流式更新远多于「最终答案」事件。

这也解释了为什么「智能体框架」容易越长越大。人们不断把产品功能（计划模式、子智能体面板、权限弹窗）塞进循环旁边。Pi 的取舍是反过来的：循环保持小，功能变成可装卸的扩展。代价是：安全与治理不会「附赠」。

为什么这样管用。 现代编码模型已经在海量「工具调用格式」上训练过。你不需要一个巨大的产品内核，也能让模型完成读改文件与跑命令。真正难的是：会话如何存、上下文如何裁、扩展如何接、进程挂了怎么办——后面几章就是在拆这些脚手架。

Pi 把脚手架拆成包

在仓库里，「Pi」是一组包，而不是一个二进制的全部含义：

  • pi-ai：多提供方模型 API 与流式协议。
  • pi-agent-core：几乎无状态的智能体循环。
  • pi-coding-agent：你安装的 pi CLI（会话、扩展、TUI、RPC、SDK）。
  • pi-durable：实验性的持久化运行框架（library，不是服务器产品）。
  • chord：应用组合运行时（服务、复制状态、RPC、插件），Durable 用来跟踪文档。

Chapter 2

Pi 作为最小机器

Pi 编码智能体的哲学写在官网上：提供原语（primitives），而不是替你决定产品功能。默认工具很少；你要的策略用扩展、技能与包自己长出来。

四件默认工具

默认工具是 read、write、edit、bash（另有平台相关能力如 PowerShell 工具路径）。没有内置的「计划模式」或「子智能体产品」——仓库里有参考扩展，但核心刻意不绑死。

为什么四个工具就够用？因为对编码模型来说，「读文件 → 改文件 → 跑命令看结果」已经覆盖了大部分软件工程闭环。搜索、规划、多代理协作当然有价值，但它们可以被表达为：更多工具、更多提示词段、或对同一循环的再次调用。Pi 把后一类表达留给扩展，而不是写进内核。手册甚至指出：省略功能里，后台 bash 连参考扩展都没有——这说明「最小」是真的最小，不是营销话术。

压缩何时触发，也可以从第一性原理理解。模型上下文窗口是硬预算。Pi 默认保留一段「储备」token（reserveTokens，默认 16384），当已用上下文超过「窗口减去储备」时自动摘要旧消息。摘要是新条目；旧条目仍在树上。于是你得到两种时间尺度：给模型看的「工作记忆」，以及给人审计的「完整档案」。企业若把会话当日志外发，必须假设其中含密钥与客户数据。

会话是 JSONL 树

会话落在 ~/.pi/agent/sessions/<cwd>/ 一类路径下，格式是 JSONL。每条条目带父节点，因此对话是一棵树，而不是只能前进的一条线。你可以 /tree 浏览分支，/fork 开新会话文件，/clone 复制分支。离开分支时可以生成摘要。重要的是：压缩（compaction）会摘要旧消息，但原条目默认不删。

图 3

会话树：分支与压缩

显示带父指针的会话树。压缩添加摘要节点。原始条目保持可用。 资料来源：docs/sessions.md；docs/compaction.md（默认 reserveTokens 16384）。

扩展、技能、包

扩展（extension）是用 TypeScript 写的、经 jiti 加载的进程内模块，拥有完整权限。你可以注册工具、命令、提供方、MCP、虚拟模型，并监听事件。若 tool_call 处理器抛错，调用会被阻断（失败关闭）。

技能（skill）遵循 agentskills.io 一类规格，用渐进披露把能力说明塞进上下文。包（package）可用 pi install npm:/git:/local 安装；带 pi-package 关键字的包会出现在 pi.dev/packages。项目级包要在项目信任之后才加载。

Codemode 与 MCP（1.0 起内置）

Codemode 让模型写一段在 QuickJS 里跑的 JavaScript。沙箱没有 Node API、文件系统、网络或定时器；对外只能通过 tools.* 与 models.*。失败前已经发生的工具调用不会自动撤销。

MCP 支持 stdio 与 streamable HTTP，以及 OAuth。用户配置在 ~/.pi/agent/mcp.json；项目配置在 .pi/mcp.json，且仅在项目信任后读取。CLI 默认启用内置 MCP；SDK 默认不启用 Codemode / MCP / tool_search——嵌入时你要显式打开。

Caution · 注意

不要把「最小内核」理解成「安全默认」。内核省略权限提示与沙箱。你必须用容器或扩展补上控制。

Chapter 3

四种入口：TUI、打印、RPC、SDK

同一个循环，可以装进终端、管道、子进程协议，或你自己的 Node/Bun 进程。选型的关键是：你要进程隔离，还是进程内控制。

Interactive TUI

默认全屏终端 UI。适合个人日常驱动。用 Enter 注入 steer（当前工具轮次后插入），Alt+Enter 排队 follow-up（本轮结束后再跑）。

Print / JSON

-p / --mode json。适合脚本与 CI 单次任务。

RPC

pi --mode rpc：JSONL over stdin/stdout，严格 LF 分帧与 id 关联。任意语言可驱动；天然进程隔离。

SDK

createAgentSession() 等 API 嵌进 Node/Bun。边界可替换（sessionManager、tools、resourceLoader…）。内置能力默认关闭。

案例：OpenClaw——嵌入，然后分叉

pi.dev 仍把 OpenClaw 当作 SDK 集成示例。但 OpenClaw 自己的文档写明：它现在拥有 @openclaw/agent-core，「不再依赖外部智能体框架包」；pi 只是遗留别名，仍依赖 pi-tui。这对公司是有用信号：Pi SDK 足以撑起大型产品；同时，深度产品化后分叉运行时是常见终点。

Chapter 4

信任问题与安全模型

Pi 明确说：不要把模型生成的命令与代码当可信输入。它也明确说：没有内置的按次权限提示。公司若默认「装上就能给全员用」，等于把 shell 交给了模型。

图 4

安全责任边界（定性）

列出 Pi 不提供的控制、提供的扩展缝，以及公司侧责任。本图为定性责任图。 资料来源：docs/security.md；README containerization；Cloudflare PiHarness 文档（Durable 无内置审批）。

项目信任不是沙箱

信任设置决定是否加载某些项目级资源（例如项目 MCP、项目包）。它不是操作系统隔离。更糟的是：AGENTS.md / CLAUDE.md 一类上下文文件可在信任之外仍被装入。扩展在进程内以完整权限运行——把第三方扩展当成要审计的代码，而不是「插件市场装饰品」。

公司侧最小策略模板

  • 在容器、Docker Sandboxes 或 Gondolin 一类 micro-VM 中运行 pi。
  • 分发内部 Pi 包：从 permission-gate、protected-paths、confirm-destructive 起步。
  • 标准化 ~/.pi/agent/settings.json：遥测、包允许列表、MCP 白名单。
  • 设置 PI_TELEMETRY=0 或策略化评估默认开启的安装遥测。
  • 禁止未审计扩展；会话文件按密钥载体管理（分享会泄漏）。
Chapter 5

为什么终端智能体不够

编码智能体把「对话记录」持久化得很好。它默认不把「这一轮进行到哪一步」持久化。进程一死，你往往只剩下半截聊天记录，以及一句：「你继续吧。」

四种进行中状态

一次真实运行里，至少有四类状态同时存在：

  1. 对话记录（transcript）：已经写下的消息与工具结果。
  2. 模型调用：正在流式生成的 token；可能已经产生费用。
  3. 工具调用：意图已发出、副作用可能已发生、结果尚未提交。
  4. 应用状态：你的 bot 业务数据（工单进度、调查笔记、审批备忘）。

经典 Pi 编码智能体主要保证第 1 类。手册里的说法很准确：它「保留对话，不保留这一轮（keeps the conversation, not the turn）」。排队中的 steer / follow-up 在内存里；工具已开始执行这件事，也可能没有耐久记录。

想象一个值班机器人正在 bash 里跑诊断脚本。脚本已对外网 API 发出请求，进程此时被 Kubernetes 杀掉。磁盘上的 JSONL 可能只有「助手说打算调用 bash」或甚至只有更早的消息；「调用已开始、stdout 写到一半」未必存在。人回来只能说「继续」，模型则可能重复副作用。Durable 的回答不是魔法：它要求你在执行前先把意图提交进存储，并承认外部世界无法回滚。

因此，「Durable」这个词在工程上必须拆开读。它耐久的是已提交的会话事实与任务检查点；它不耐久未提交的流式碎片；它也不自动耐久外部系统的业务约束。公司若把口号听成「恰好一次、永不丢、可断电」，就会在 SQLite synchronous=NORMAL 与不安全重放上栽跟头。

公司级工作负载——Slack 值班机器人、持续数小时的调查、多个人同时引导同一智能体、Kubernetes 驱逐后继续跑——需要的不是「更强的提示词」，而是把可见事实都变成已提交状态。这就是 Pi Durable 要解决的问题。

Chapter 6

Durable 的一条规则

规范里的核心句只有一句：Session 原子地提交不可变条目、完整任务记录，以及 Chord 跟踪的文档。只有已提交状态可被观察。

这句话几乎决定了后面所有 API 形状。若 UI 能显示一条「工具正在跑」的输出，那么这条输出必须已经（按节流间隔）进过存储；否则崩溃后会出现「用户见过、系统否认」的幽灵状态。反之，事务内禁止直接做网络调用：因为事务可能回滚，而网络请求不会回滚。于是副作用必须夹在两次提交之间——这就是下一章的三明治。

「毒化」机制同样来自这句话。当存储层返回不确定结果（例如写入是否成功未知）时，内存里的 Session 不再可信。继续用它，就会在「已提交」与「未提交」之间撒谎。唯一诚实的动作是 close，再从存储 reopen。宿主监督程序必须把 poison 当成一等故障信号，而不是普通异常。

分层

从上到下：

  1. Host（宿主）：你的应用进程、进程监督、身份、传输层。
  2. Harness：对话句柄、投递收件箱、任务调度、视图。
  3. Session 内核：一条变更行（mutation line）、Chord 文档跟踪。
  4. Storage：Memory / SQLite / JSONL（或通过一致性测试的自定义后端）。
图 6

Pi Durable 分层

显示 Host 到 Storage 的四层结构。宿主拥有进程与身份。Harness 拥有调度与收件箱。 资料来源：Durable 手册 §1.2；packages/durable/README.md。

八条不变式里，公司最该记住的几条

  • 先写入存储，再对外发布；不做「可见但不耐久」的发布。
  • 副作用（调用外部世界）发生在事务之外。
  • ID 不可变。
  • 若存储结果不确定，Session 被毒化（poison）：必须关闭并重新打开，不能 catch 了继续用。

一次输入大约十七次提交

手册用捕获工具集演示：用户一条输入、模型调用一次工具，大约经历 17 次提交——创建对话与文档、写入用户条目、创建 generation / tool 任务、提交工具意图、提交工具结果与助手消息等。数字来自该捕获，不是性能 SLA；它说明的是设计密度：每个对外可见的事实都应对应一次可恢复的提交。

图 7

一次工具调用的提交骨架（示意）

显示一次输入到工具结果的主要提交阶段。完整捕获约十七次提交。本图为教学压缩。 资料来源：Durable 手册 §1.4；spec 核心规则。
为什么这样管用。 崩溃恢复不必「猜模型想到哪了」。只要重新打开存储，调度器就能根据已提交的任务检查点继续。你看到的任何 UI 状态，都应当能从存储重建——这比「再问模型一次你做到哪了」可靠得多。
Chapter 7

工作即任务：副作用三明治与重放

Durable 把进行中的工作建模为带检查点的状态机（任务）。外部世界的动作夹在两次提交之间：先提交意图，再执行，再提交结果。这叫副作用三明治（effect sandwich）。

任务生命周期

用 defineTask(kind, version, initial, phases, abort, migrate?) 定义。状态包括 pending / running / waiting / completing / terminal；结局包括 completed / failed / aborted / orphaned / faulted。一步若没有改变检查点，任务会因「无耐久进展」被 faulted。sleep 不是耐久的——deadline 应写进检查点。

可安全重放 vs 不可安全重放

工具默认 replay: "unsafe"。崩溃恢复后，模型会收到一个 interrupted 结果，而不是自动再跑一遍。只有你确认工具幂等时，才标 "safe" 并允许重跑。内置的 read / write / edit / bash 都是 unsafe。外部副作用不会回滚。被打断的模型请求「可能付两次钱」。

把三种崩溃位置分开想，会清楚很多：

  1. 意图提交前崩溃：外部无事发生；重开后就像没开始。
  2. 意图已提交、效果执行中/后、结果未提交：外部可能已变；重开时任务停在 intent 阶段。Unsafe 工具告诉模型「中断了」；Safe 工具可能再执行一次——所以 Safe 意味着幂等，而不是「框架会去重」。
  3. 结果已提交后崩溃：事实已在对话里；恢复后继续下一阶段。

博文里「requestId 让投递恰好一次」指的是第 0 步：同一投递不会被收件箱接受两次。它不覆盖第 2 种位置里的工具效果。HN 上的争论，本质是术语「exactly-once」被用在了不同层。

Warning · 警告

不要把 requestId 的「恰好一次接受」理解成工具副作用恰好一次。requestId 是投递幂等键。工具效果仍要靠你的幂等键与补偿。

内置任务与所有权

内置任务包括 pi.generation、pi.tool、pi.compaction。所有权树保证中止向下级联，abort 处理自下而上。调度器不会只因为注册表里缺代码就把任务标成终态——它会保持 pending 并显示 blocked，直到你装回对应扩展。这保护了数据，也意味着升级/热更新策略必须由你设计。

Chapter 8

对话、分叉、文档与扩展注册表

Durable 的对话是按时间排列的不可变条目列表。分叉挂在另一条对话的某个条目上，继承历史但不复制。应用状态则是类型化的 JSON 文档，由 Chord 以基线 + 增量方式跟踪。

分叉、重置、交接

重置与交接只向前移动 head 标记，不删除历史。Cloudflare 文档也确认：目前还不能删除对话。Mario Zechner 在 HN 上说：「树还在，只是更扁了。」编码智能体的逐条 parent 树，与 Durable 的扁平对话 + 分叉祖先，是两种会话模型；公开迁移路径未见文档。

编码智能体树 vs Durable 分叉（定性）

每条条目有 parentId。UI 可浏览备选分支。适合个人探索。

对话为线性不可变列表。分叉共享前缀历史。适合多表面长期应用。

对比两种会话模型。不要假设会话文件可自动迁移。 资料来源：docs/sessions.md；Durable 手册 §3；HN 讨论（maintainer）。

文档（documents）

defineDoc 设定 scope（session / conversation / task）、history（latest / rewindable）、fork 策略（current / initial / asOf）、以及可选 migrate / checkpointWhen。没有 checkpointWhen 时，增量会一直增长。内置文档包括 pi.agent、pi.provider、pi.live、pi.inbox、pi.usage。

扩展注册表：进程内代码，持久化的只是名字

扩展是 {name, tools, sections, hooks, wraps, tasks}，安装进从不持久化的进程本地注册表。对话只保存扩展名字；未安装的名字会被静默跳过。七个钩子（beforeRequest、afterResponse、onYield、afterTools、beforeTool、afterTool、beforeCompact）都按扩展选择生效——没有全局钩子。你的权限扩展若没被该对话选中，防护就不存在。

这个设计对热更新极友好：同名再 install 一次即重载；正在跑的阶段继续用旧代码，到阶段边界才切到新代码。但对安全极不友好：持久化层无法证明「当时防护在场」。审计日志必须由宿主自己写。升级时若改了扩展名，旧对话会静默失去工具与钩子——属于规范里强调的 footgun。

子智能体在 Durable 里也不是一等 API，而是模式：前台子智能体是被调用工具任务拥有的子对话；后台则用锚点任务 + 报告任务。度假规划 demo 展示了如何把 safe 重放与后台工作拼起来。公司若需要「官方子代理产品」，要么自己做模式，要么选别的栈。

Warning · 警告

把权限扩展做成「可选」等于把安全做成「可选」。在宿主层强制安装，并在创建对话时默认选中。

收件箱：steer / follow-up / reject

投递是 input 或 write；忙碌时策略 whenBusy 为 steer、followUp（默认）或 reject。requestId（每对话）或 Cloudflare 上的 operationId 充当幂等键。多个人「一起引导」的真实含义是：多个客户端连到同一个拥有存储的进程，由它扇出视图——不是多写者合并（那是明确非目标）。

Chapter 9

存储与部署：Node、Bun、Cloudflare

Durable 是库，不是托管服务。你选存储后端，并保证「同一时间只有一个进程拥有该存储」。Cloudflare 的 PiHarness（beta）把这件事嵌进 Durable Object。

三种内置后端

后端耐久含义手册基准（M3 Max，定性排序）
Memory进程退出即失lookup ~0.44 µs；commit ~5.5 µs
SQLite（推荐）WAL + synchronous=NORMAL：断电/主机故障时最新提交可能丢commit ~120 µs；重开 1k 条目 ~1.33 ms
JSONL默认 fsync 关；撕裂尾会截断；损坏不自动修commit ~792 µs；重开 ~249 ms

一致性测试套件（存储约 23 例；执行环境手册写 21 例，1.0.4 又扩展了 watch 行为）是自定义后端/环境的门禁。两个进程打开同一 SQLite 文件可能铸造重复 ID并毒化记录。

Source note · 资料说明

博文「从灾难中恢复」与 SQLite NORMAL 语义之间存在张力。工程上应理解为：默认偏进程崩溃耐久，不是保证的断电耐久。可调同步设置，或接受风险。Cloudflare DO 的 SQLite 语义可能更强，但未在本材料中独立验证。

Cloudflare PiHarness（beta）

2026-10-02 宣布。它在 Agents SDK 的 Lifecycle 能力里运行 Pi Durable，用 Durable Object 的 SQLite（表前缀 pi_），并用 heartbeat job 唤醒对象。你仍自选 WebSocket / HTTP / RPC 传输。

  • 心跳约每 30 秒；驱逐、崩溃或部署（约 30 秒宽限期）后由 alarm 拉起并 reopen。
  • 单次 alarm 调用最长约 15 分钟，约每 10 分钟交接；单次模型流超过 15 分钟可能被切断。
  • 根 session id 为 "1"；建议一用户/一对话一个 DO。
  • 无事件游标、无优雅排空、尚无对话删除、尚无内置审批。

许可与治理

  • 已发布包为 MIT（LICENSE © 2025 Mario Zechner）。evals 未许可。
  • 商标与项目归属 Earendil Works。核心「MIT, forever」被作者称为不可谈判；未来可能有 Fair Source 增值与专有企业/云能力（「尚未构建」）。
  • 无 CLA / DCO。新贡献者的 issue/PR 默认自动关闭，每日审阅——上游修复可能需要既有关系，或你自己 fork/patch。
  • Radius（radius.pi.dev，early alpha）已接入 /login、/share、/bug。

遥测默认

enableInstallTelemetry 默认为 true（匿名安装/更新报告与部分提供方归因头）。enableAnalytics 默认 false。退出：PI_TELEMETRY=0；减少自动网络：PI_OFFLINE=1 或 --offline。精确载荷细节在本材料中未完整文档化——上线前应自行抓包验证。

治理上还有两件「慢变量」。其一是贡献门闩：新贡献者 PR 默认关闭，意味着你不能假设紧急 CVE 修复会从社区很快涌入；要有私有补丁分支能力。其二是开源核心之上的商业层：Radius 已出现在登录与分享路径里；Fair Source / 专有层「尚未构建」但已被宣示。MIT 允许分叉，却不能阻止商标与云服务分化——采购与法务应把「核心库」和「托管体验」写成两行风险。

成熟度叙事也要拆开：编码智能体 1.0 之后仍出现 patch 级 Breaking（例如 Azure 提供方重命名）；Durable 则明文 experimental，且 1.0.3/1.0.4 连续 Breaking（ExecutionEnv 合同）。对 SemVer 的企业直觉在这里不适用：精确 pin + 读 CHANGELOG + 跑一致性测试才是合同。

90 日试点计划（STE）

  1. 第 1–2 周：用托管安装或 Nix 部署编码智能体。锁定 settings。仅在沙箱中运行。
  2. 第 3–4 周：发布内部权限包。选定 5–10 名工程师。收集失败模式。
  3. 第 5–6 周：若需要嵌入，先 RPC 后 SDK。保持工具显式开启。
  4. 第 7–10 周（可选 Durable）：用 SQLite 做内部 triage/Slack 试点。实现身份与 beforeTool 审批。运行一致性测试。
  5. 第 11–12 周：做崩溃演练与版本升级演练（故意升到含 Breaking 的 patch）。写去留报告。
